# FlowDesk 业务模型

## 1. 阶段目标与边界

**已确认**：本阶段从 `docs/kickoff.md` 已确认的需求中提炼业务概念、职责、关系和约束，为后续技术架构、数据库和 API 设计提供稳定依据。

本阶段只描述“业务上有哪些对象，以及它们如何协作”，不确定数据库表、字段类型、接口路径、类结构或框架实现。

当前状态：业务模型已完成。

## 2. 核心业务概念

| 概念 | 业务含义 | v1 中的职责 |
| --- | --- | --- |
| 用户 | 能够登录 FlowDesk 的企业内部人员 | 以被授予的角色参与工单或维护系统配置 |
| 角色 | 用户在系统中承担的职责 | v1 包含普通员工、IT 支持人员和系统管理员 |
| 工单 | 一次 IT 服务请求从提交到结束的完整生命周期 | 承载问题、状态、责任归属、处理过程和最终结果 |
| 工单分类 | 对问题所属 IT 服务类型的单级划分 | 用于提交选择、查询和简单统计 |
| 优先级 | 表示工单处理紧迫程度的业务属性 | 用于排序、筛选和简单统计，不承诺 SLA |
| 工单记录 | 工单生命周期中不可覆盖的业务事实 | 保存沟通、处理、状态变化、责任变化及结束原因 |
| 附件 | 随问题描述或员工补充信息提交的文件 | 为有权限的人提供处理上下文 |
| 工单关联 | 两张工单之间具有明确方向和含义的联系 | 表达后续工单引用或重复工单指向 |

## 3. 用户与角色

### 3.1 普通员工

**已确认**：普通员工是工单提交人，可以创建和查看自己的工单，并在业务允许时补充信息、确认解决、反馈未解决或撤销工单。

### 3.2 IT 支持人员

**已确认**：IT 支持人员是工单处理者，可以查看公共待受理工单并自主领取。领取后，当前负责人负责记录过程、请求补充、提交解决结果、转交或异常关闭。

### 3.3 系统管理员

**已确认**：系统管理员维护用户、角色、工单分类和必要基础配置，默认不查看具体工单内容，也不参与工单处理。账号停用或角色移除需要更换活动工单负责人时，管理员只能执行最小范围的管理性交接。

### 3.4 用户与角色关系

**已确认**：一个用户在 v1 中可以同时拥有多个角色，权限按照角色组合。系统管理员角色本身不授予工单查看或处理权限；同一用户同时具有 IT 支持人员角色时，才可以按照 IT 支持人员的参与关系访问和处理工单。

## 4. 工单

### 4.1 工单职责

**已确认**：工单是核心业务对象。一张工单只表示一次完整处理生命周期，具有独立编号，并始终保留提交人、当前状态、历史责任归属和全部业务记录。

工单至少需要表达以下已确认信息：

- 唯一工单编号。
- 提交人和提交时间。
- 问题描述。
- 单级分类。
- 优先级。
- 当前状态。
- 当前负责人或最后负责人。
- 创建时及后续产生的附件。
- 处理过程、补充信息、解决结果和关键操作记录。
- 适用时的确认期限、补充期限、结束方式和结束原因。
- 适用时与另一张工单的关联。

### 4.2 工单状态

**已确认**：v1 包含七个互斥状态。

| 状态 | 是否终态 | 负责人规则 |
| --- | --- | --- |
| 待受理 | 否 | 没有负责人 |
| 处理中 | 否 | 必须有当前负责人 |
| 待补充 | 否 | 必须有当前负责人 |
| 待确认 | 否 | 保留当前负责人 |
| 已完成 | 是 | 保留最后负责人 |
| 已取消 | 是 | 可能没有负责人；已有负责人时保留最后负责人 |
| 已关闭 | 是 | 保留最后负责人 |

终态工单不能恢复或重新打开。仍需处理时必须创建具有新编号和独立生命周期的新工单。

### 4.3 当前负责人

**已确认**：当前负责人表示此刻承担 IT 处理责任的用户，只能是状态正常且可以处理工单的 IT 支持人员。

- 待受理工单没有当前负责人。
- 领取成功后，领取人成为当前负责人。
- 直接转交会原子地替换当前负责人，不能出现无人负责的中间状态。
- 只有当前负责人可以执行 IT 处理操作。
- 工单结束后不再存在待履行的处理责任，但保留最后负责人作为历史信息。

### 4.4 工单提交信息

**已确认**：v1 将标题、问题描述、分类和优先级设为必填信息，附件及原工单引用为可选信息。标题用于列表识别，问题描述承载详细情况；分类和优先级用于处理、筛选与统计。

## 5. 工单记录

### 5.1 记录原则

**已确认**：工单记录按发生顺序组成完整时间线。已经发生的记录不能被覆盖或删除；需要修正时，应产生新的业务记录。

每条记录应能够说明：

- 发生了什么业务动作。
- 动作由哪名用户或系统执行。
- 动作发生时间。
- 动作要求填写的正文或原因。
- 必要时的原状态、新状态、原负责人和新负责人。
- 随该动作提交的附件。

### 5.2 记录类型

v1 需要区分以下业务记录：

| 记录类型 | 主要内容 |
| --- | --- |
| 创建记录 | 提交人、问题信息和初始附件 |
| 领取记录 | 领取人和领取时间 |
| 处理记录 | 当前负责人记录的排查、沟通或处理内容 |
| 转交记录 | 原负责人、新负责人和转交原因 |
| 管理性交接记录 | 因负责人账号停用或移除 IT 角色产生的原负责人、新负责人和交接原因 |
| 补充请求 | 请求内容、发起人、发起时间和补充截止时间 |
| 员工补充 | 补充正文、附件、提交人和提交时间 |
| 补充请求撤回 | 撤回人、撤回原因和撤回时间 |
| 解决结果 | 本次处理结论、提交人、提交时间和确认截止时间 |
| 未解决反馈 | 提交人的未解决原因和反馈时间 |
| 完成记录 | 员工主动确认或系统超时完成，并明确完成方式 |
| 取消记录 | 提交人的撤销原因和撤销时间 |
| 关闭记录 | 手动或自动关闭方式、标准原因、具体说明和关闭时间 |

同一工单可以具有多次转交、多轮补充请求、多份解决结果和多次未解决反馈，每次都保留为独立记录。

## 6. 分类与优先级

### 6.1 工单分类

**已确认**：v1 使用简单的单级分类，不建立父子层级。员工提交工单时必须选择分类，系统管理员负责维护可选分类。

**已确认**：已经被工单使用的分类只允许停用、不允许删除；停用后不能用于新工单，但历史工单继续显示原分类。

- 系统管理员可以创建、重命名、启用和停用分类。
- 分类名称必填且不能与现有分类重名，避免员工选择时产生歧义。
- 未被任何工单使用的分类可以删除；已被使用的分类只能停用。
- 停用分类不能用于新工单，也不能作为负责人调整分类时的目标。
- 分类重命名不会改变工单与分类的归属关系。

### 6.2 优先级

**已确认**：每张工单具有一个优先级，用于列表排序、筛选和简单统计。优先级不产生处理时限、催办或自动升级，因此不构成 SLA。

**已确认**：v1 使用“低、中、高”三级优先级，默认值为“中”。员工提交时可以选择，当前负责人可以在工单处于“处理中”或“待补充”时调整，但必须填写原因并留下记录。

## 7. 附件

**已确认**：附件只能依附于一张工单中的创建记录或员工补充记录，附件本身不脱离工单独立流转。v1 不把 IT 处理记录上传附件作为已确认能力。

- 只有能够查看所属工单的用户才能访问附件。
- 附件访问不能绕过工单权限。
- 工单进入终态后，附件继续作为历史内容保留。
- v1 只支持受限制的常见图片和文档；具体类型、大小、数量和存储方式在工程准备阶段确定。

## 8. 工单关联

**已确认**：工单关联必须具有明确方向，且不会合并两张工单的生命周期、状态、负责人、分类、优先级、描述或附件。

v1 包含两种业务含义：

| 关联含义 | 来源工单 | 目标工单 | 约束 |
| --- | --- | --- | --- |
| 后续工单引用 | 新创建的工单 | 提交人有权查看的原工单 | 可选，仅用于提供上下文 |
| 重复工单指向 | 被关闭的重复工单 | 同一提交人的另一张有效工单 | 关闭原因为“重复工单”时必填，不能指向自身 |

关联只提供上下文，不使用户获得目标工单之外的额外访问权限。

## 9. 核心关系

| 来源 | 关系 | 目标 | 数量与约束 |
| --- | --- | --- | --- |
| 用户 | 拥有 | 角色 | 一个用户拥有一个或多个角色，权限按角色组合 |
| 普通员工 | 提交 | 工单 | 一个员工可以提交多张；一张工单只有一个提交人 |
| IT 支持人员 | 负责 | 工单 | 一名 IT 可负责多张；活动工单最多一个当前负责人 |
| 工单 | 归属 | 工单分类 | 一张工单一个分类；一个分类可被多张工单使用 |
| 工单 | 具有 | 优先级 | 一张工单一个当前优先级 |
| 工单 | 包含 | 工单记录 | 一张工单至少包含创建记录，记录只能属于一张工单 |
| 工单记录 | 携带 | 附件 | 创建记录和员工补充记录可有多个附件，附件只属于一个业务上下文 |
| 工单 | 关联 | 工单 | 仅允许已确认的两种有向关联含义 |

## 10. 生命周期不变量

以下规则在后续数据库、API 和代码设计中都必须成立：

1. 一张工单始终只有一个提交人，提交后不能更换。
2. 一张工单任一时刻只能处于一个状态。
3. 待受理状态没有负责人；处理中、待补充和待确认状态必须有负责人。
4. 当前负责人必须是有效且可以处理工单的 IT 支持人员。
5. 只有当前负责人能够推进 IT 处理流程。
6. 已完成、已取消和已关闭均为不可重开的终态。
7. 已发生的处理、解决、转交、补充和结束记录不能覆盖或删除。
8. 自动完成与主动确认必须能够区分，手动关闭与自动关闭也必须能够区分。
9. 同一工单上的互斥状态或负责人变更并发发生时，只能有一个成功。
10. 查看工单、记录、附件和关联信息时必须遵守同一权限边界。

## 11. 第一轮确认结论

**已确认**：业务模型第一轮采用以下规则：

1. **用户角色**：一个用户可以同时拥有多个角色；权限按角色组合，但工单查看仍受提交人、当前负责人或历史参与关系限制。
2. **工单提交字段**：标题、问题描述、分类和优先级必填，附件及原工单引用可选。
3. **分类停用**：已被使用的分类不能删除，只能停用；停用不影响历史工单，新工单不可再选。
4. **优先级规则**：采用低、中、高三级，默认中；员工提交时可选，当前负责人在处理中或待补充时可调整并必须填写原因。

以上规则已纳入对应业务概念，后续技术设计必须保持一致。

## 12. 账号、角色与工单信息变更

### 12.1 账号和角色状态

**已确认**：v1 采用以下账号和角色变更规则：

- 用户账号只有“启用”和“停用”两种可用状态；停用后不能登录或执行任何新操作，但历史身份和记录必须保留。
- 用户账号不做物理删除；不再使用的账号通过停用处理。
- 每个账号至少保留一个角色，不能移除账号的最后一个角色。
- 停用账号不能领取工单，也不能成为转交目标。
- 普通员工账号停用后，其未结束工单不自动取消，继续按照已有流程和超时规则处理。
- 停用账号或移除 IT 支持人员角色时，如果该用户仍负责未结束工单，系统管理员必须为每张相关工单指定符合条件的有效 IT 支持人员作为接替人；不同工单可以指定不同接替人，全部交接成功后才能完成账号或角色变更。
- 管理性交接只用于账号和角色维护，不属于日常工单转交。系统管理员只能看到完成交接所需的工单编号、状态和当前负责人等最小信息，不能借此查看问题正文、附件或处理内容。
- 管理性交接不改变工单状态、补充期限或确认期限，每张受影响工单都必须保留原负责人、新负责人、管理员、交接原因和时间。
- 如果没有可用接替人，则不能完成涉及活动负责人的 IT 角色移除；账号安全停用需要先创建或启用可接替的 IT 支持人员，并在同一操作中完成交接。
- 为避免系统失去管理入口，禁止停用最后一个已启用的系统管理员，也禁止移除其系统管理员角色。
- 移除普通员工角色不会取消该用户已经提交的工单，但该用户不再能够执行员工侧操作，未结束工单继续按照已有流程和超时规则处理。
- 新增、移除角色或停用账号都不改变该用户已经产生的历史工单记录。

### 12.2 多角色用户处理自己的工单

**已确认**：同时具有普通员工和 IT 支持人员角色的用户不能领取自己提交的工单，也不能成为自己工单的业务转交或管理性交接目标。这样可以避免同一人同时充当提交人、处理人和确认人，使演示流程及责任记录保持可信。

### 12.3 提交后的工单信息

**已确认**：工单提交后，员工不能直接覆盖标题、问题描述、分类、优先级或既有附件；新增信息必须通过补充记录保留变化过程。当前负责人可以在“处理中”或“待补充”状态调整分类和优先级，但必须填写原因并留下独立记录；标题和原问题描述始终保留。

这些规则的取舍如下：账号停用不会破坏历史数据，但仍负责活动工单时必须同时完成管理性交接；禁止处理自己的工单牺牲少量灵活性，换取清晰的职责分离；提交后不覆盖原始信息会增加记录数量，但能够保证问题描述和业务变化可追溯。

## 13. 第二轮审核结论

**已确认**：本轮由 Codex 根据既有业务边界完成审核，采用以下规则：

1. **账号与角色变更**：采用 12.1 的启用、停用、管理性交接和最后管理员保护规则。
2. **职责分离**：多角色用户不能领取或接收自己提交的工单。
3. **信息变更**：提交人只能追加补充；当前负责人仅可在处理中或待补充时调整分类和优先级，并记录原因。

审核同时修正并补足了以下模型细节：每张工单至少具有一条创建记录；只有创建记录和员工补充记录可以携带 v1 附件；用户账号不做物理删除；分类和账号状态变化不得破坏历史工单；账号停用导致的活动工单责任变化使用独立的管理性交接记录。

## 14. 本阶段验收结论

**已确认**：FlowDesk 业务模型阶段已经完成，并通过以下验收检查：

- 核心业务概念的含义和职责明确。
- 用户、角色、工单、分类、记录、附件和工单关联之间的关系明确。
- 工单生命周期不变量明确且与 kickoff 规则一致。
- 用户及基础配置变更对活动工单的影响明确。
- 文档不存在影响技术设计的“暂时假设”或“待确认”项。
- 尚未提前确定数据库表、API 或具体代码结构。

业务模型完成后，项目可以进入技术架构设计阶段。技术设计必须以本文档和 `docs/kickoff.md` 为依据，不得改变已确认的业务含义。
