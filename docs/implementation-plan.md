# FlowDesk 开发任务拆分

## 1. 文档目标与状态

本文把已经确认的需求、业务模型、架构、数据库、API 和工程准备方案转换为可执行的开发顺序。任务优先按可演示、可测试的纵向业务能力组织，必要的工程底座只保留在第一个里程碑中。

**已确认**：2026-09-07，本文所列 7 个里程碑、20 项任务、依赖顺序、验收标准、测试要求和 Git 检查点通过集中验收。后续按里程碑逐项实施，不在未确认的情况下扩大 v1 范围。

## 3. 拆分原则

1. 每个业务里程碑都必须形成可通过 API 或页面观察的结果，不把 Controller、Service、Mapper 分成三个互不完整的交付。
2. 后端业务规则先通过单元或集成测试证明，再由页面接入；前端不承担最终权限和状态校验。
3. 数据库变化只通过 Flyway 新迁移推进；迁移、后端枚举、权限编码和 API 契约保持同步。
4. 涉及工单写入时，快照、不可变记录、参与关系和关联关系必须在同一 MySQL 事务内完成。
5. 涉及 Redis 或文件系统时，必须同时实现失败路径和故障测试，不能把补偿留给未定义的后续工作。
6. 每个里程碑在独立短期分支完成检查后，通过 PR 进入 `main`；提交只是检查点，不代表验收通过。
7. 不在本计划中加入微服务、消息队列、Kubernetes、对象存储、AI、通用工作流引擎或其他 v1 非目标。

## 6. M0：工程底座

目标：建立最小但完整的构建、运行、迁移和测试入口，使后续每个业务任务都能在同一基线上验证。

### TASK-001：初始化可重复运行的仓库骨架

- 能力：`CAP-09`。
- 依赖：本计划验收；当前终端实际版本达到 Node.js 24.20.0、pnpm 12.3.4；Java、Docker 和 Git 复核通过。
- 工作：创建单模块 Spring Boot Maven 工程、Maven Wrapper、Vue/Vite/TypeScript 工程、固定 pnpm、MySQL/Redis Compose、Profile 配置骨架、`.env.example`、`.gitignore` 和健康检查入口。
- 验收：仓库不含真实密钥；Compose 只启动 MySQL/Redis；后端和前端可在宿主机启动；前端 `/fd` 代理正确；停止重启不丢基础设施数据。
- 测试：Wrapper/version 命令、`docker compose config`、后端上下文启动测试、前端 lint/typecheck/unit/build 空基线、健康检查冒烟。
- 完成定义：Windows 本地与 Linux CI 使用相同脚本名；README 启动入口与实际命令一致；无业务表和业务页面提前实现。
- Git 检查点：先记录验证命令和结果，再提交 `chore: initialize application workspace`。

### TASK-002：实现 Flyway 数据基线与确定性测试数据

- 能力：`CAP-02`、`CAP-09`。
- 依赖：`TASK-001`。
- 工作：编写 V1 的 11 张表、约束、外键和索引，编写 V2 的角色/权限映射；建立仅 demo/test 启用的可重复数据入口；禁止 ORM 自动建表。
- 验收：MySQL 8.4.11 空库可完整迁移；V2 编码与文档一致且无重复；prod 不扫描 demo 数据；公共迁移不创建默认管理员密码。
- 测试：Testcontainers 空库迁移、schema history、关键约束/索引、V2 完整性、demo 数据重复运行；非法状态、非法负责人关系和重复 submission key 的数据库约束测试。
- 完成定义：迁移不可依赖本机路径、时区或不稳定当前时间；从已迁移数据库执行 `validate` 成功。
- Git 检查点：测试全绿后提交 `feat: establish database migration baseline`。

### TASK-003：建立后端公共契约与 CI 基线

- 能力：`CAP-09`，为全部业务能力提供公共入口。
- 依赖：`TASK-001`、`TASK-002`。
- 工作：实现 `R<T>`、分页模型、统一异常映射、字段校验、traceId、UTC 时间、OpenAPI 基础、安全日志过滤、测试分层配置和 GitHub Actions 三 Job 骨架。
- 验收：错误响应不泄露堆栈/SQL/密钥；local/demo 开启 OpenAPI、prod 关闭；测试命名进入正确 Maven 生命周期；CI 使用固定 JDK/Node/pnpm。
- 测试：MockMvc 验证 400/401/403/404/409 基础形状与 traceId；日志脱敏测试；`mvnw verify` 和全部 pnpm 基线脚本；干净检出 CI 冒烟。
- 完成定义：JaCoCo 门槛已配置但不得靠排除业务包规避；没有用空洞测试伪造覆盖率。
- Git 检查点：CI 及本地入口通过后提交 `chore: establish quality and api foundations`。

M0 阶段验收：新开发者可从空库启动工程；公共迁移和基础 CI 可重复运行；尚未实现具体业务流程。

## 7. M1：身份入口

目标：交付第一个可从页面演示的纵向能力——用户登录、恢复身份和退出。

### TASK-010：实现认证、会话和密码安全

- 能力：`CAP-01`。
- 依赖：`TASK-003`；测试夹具具备三类用户。
- 工作：实现 Argon2id 密码封装、登录、HS256 Access Token、Redis 会话与 Refresh Token 摘要、刷新轮换/重用检测、退出、`/auth/me` 和当前用户修改密码。
- 验收：Access Token 15 分钟且只由 JSON 返回；Refresh Cookie 为 HttpOnly、7 天、限定路径并校验 Origin；登录失败不暴露账号状态；重复退出幂等；改密撤销全部会话。
- 测试：Argon2 参数单测；登录和 Security MockMvc；真实 Redis 的刷新轮换、旧 Token 重用、过期和撤销集成测试；Cookie/Origin 负向测试；敏感日志检查。
- 完成定义：所有认证接口符合 API 文档；Redis 失败时的改密行为遵循保守失败顺序；OpenAPI 不展示敏感值。
- Git 检查点：安全与集成测试通过后提交 `feat: implement secure authentication sessions`。

### TASK-011：实现 Vue 登录外壳与身份恢复

- 能力：`CAP-01`。
- 依赖：`TASK-010`。
- 工作：实现 `/login`、应用布局、Pinia 内存身份、Axios Bearer 注入与单次刷新协调、路由守卫、账号菜单改密/退出、403 和 404 页面。
- 验收：Access Token 不进入 localStorage/sessionStorage/Cookie；刷新成功恢复请求；刷新失败清空内存并回登录；无权限路由不展示但不替代后端鉴权。
- 测试：Vitest 覆盖权限判断、刷新并发协调和错误转换；组件测试覆盖登录/改密校验；Playwright 覆盖登录、刷新恢复、退出和 403。
- 完成定义：刷新风暴被合并为一次 refresh；409 不自动重放写操作；页面不输出敏感字段。
- Git 检查点：前后端纵向登录场景通过后提交 `feat: deliver authenticated application shell`。

M1 阶段验收：三类用户可以登录，刷新后恢复身份，退出或改密后旧会话不可继续使用。

## 8. M2：员工提交与查询

目标：让普通员工能够提交真实工单，并在页面持续查看其业务事实。

### TASK-020：提供分类选项与工单查询基础

- 能力：`CAP-02`、`CAP-03`。
- 依赖：`TASK-010`。
- 工作：实现启用分类选项、工单可见性策略、四种显式 `scope`、固定筛选/排序/分页，以及详情 `allowedActions` 计算基础。
- 验收：用户不能通过传入他人 ID 扩大范围；无权工单统一 404；公共队列、本人提交、本人负责和历史参与范围含义稳定；优先级不是字符串排序。
- 测试：Mapper/自定义 SQL 集成测试、权限矩阵参数化测试、分页稳定性和最大 size 测试、403/404 隐藏策略测试。
- 完成定义：查询计划与数据库索引映射一致；响应不返回正文或无关敏感字段。
- Git 检查点：查询及权限测试通过后提交 `feat: establish ticket visibility and queries`。

### TASK-021：实现幂等创建与附件原子写入

- 能力：`CAP-03`。
- 依赖：`TASK-020`；附件目录同卷和原子移动能力已由启动检查验证。
- 工作：实现 multipart 工单创建、submission key 防重、业务编号、创建记录、可选后续工单关系、附件白名单/限额/摘要，以及暂存→事务→原子移动→提交顺序。
- 验收：同一用户同一 submission key 只生成一张工单；附件任一步失败不留下已提交业务事实或不可解释文件；无权原工单不能关联；成功后状态为 `PENDING`、负责人为空。
- 测试：创建 happy path、并发/重试幂等、分类停用、关联权限、附件类型/大小/数量/路径穿越、第一/中间/最后移动失败、MySQL 提交失败和清理失败故障测试。
- 完成定义：快照、首条记录、关联和附件元数据满足同一事务要求；客户端文件名从不参与真实路径。
- Git 检查点：真实 MySQL 与临时文件系统故障测试通过后提交 `feat: create tickets with atomic attachments`。

### TASK-022：实现详情、时间线和受控附件下载

- 能力：`CAP-03`。
- 依赖：`TASK-020`、`TASK-021`。
- 工作：实现工单详情、按 sequenceNo 的分页时间线、关联摘要和嵌套工单路径附件下载。
- 验收：详情返回当前快照与 allowedActions；时间线不可变且顺序稳定；下载重新验证工单可见性和附件归属；响应强制下载并设置 nosniff。
- 测试：提交人/公共队列 IT/当前及历史参与人/无权用户权限组合；附件跨工单 ID、缺失文件和安全响应头；时间线分页稳定性。
- 完成定义：不暴露内部工单主键或磁盘路径；无权与不存在统一为 404。
- Git 检查点：查询和下载安全测试通过后提交 `feat: expose ticket detail timeline and downloads`。

### TASK-023：交付员工工单页面

- 能力：`CAP-03`。
- 依赖：`TASK-021`、`TASK-022`。
- 工作：实现 `/tickets`、`/tickets/new`、`/tickets/:ticketNo` 的员工视角，包括筛选、创建表单、submission key 生命周期、附件校验、后续工单选择、详情和时间线。
- 验收：员工可完整创建并看到新工单；重复点击或网络重试不制造重复工单；错误、上传限制和不可见资源提示明确；刷新后仍可重新查询业务事实。
- 测试：Vitest 表单和错误映射；组件测试覆盖附件与筛选；Playwright 覆盖登录→创建带附件工单→列表→详情→下载。
- 完成定义：页面只消费已定义 API；没有只在前端实现的业务不变量。
- Git 检查点：员工纵向 E2E 通过后提交 `feat: deliver employee ticket submission flow`。

M2 阶段验收：员工能创建一张带分类、优先级、可选附件和关联的工单，并安全查看列表、详情、历史和附件。

## 9. M3：IT 处理闭环

目标：完成工单从公共队列进入处理、沟通、解决和终态的全部人工路径。

### TASK-030：实现领取、处理、调整和转交

- 能力：`CAP-04`。
- 依赖：`TASK-022`。
- 工作：实现 claim、add-processing-record、change-category、change-priority、transfer 和转交候选人；统一状态、负责人、版本条件更新和参与关系维护。
- 验收：并发领取只有一个成功；只有当前负责人可处理；转交原子替换负责人且不改变状态；原负责人失权、新负责人成为参与者；每个动作追加不可变记录。
- 测试：领域状态机单测；真实 MySQL 并发领取/转交/处理冲突；候选人过滤；分类/优先级校验；409 最小冲突响应。
- 完成定义：快照、record sequence、记录和 participant 同事务；动作失败没有部分写入。
- Git 检查点：并发与事务测试通过后提交 `feat: support ticket ownership and processing`。

### TASK-031：实现员工补充循环

- 能力：`CAP-05`。
- 依赖：`TASK-030`、`TASK-021` 的附件组件。
- 工作：实现 request-supplement、supplement、withdraw-supplement-request；计算 7×24 小时截止时间；补充正文与附件复用安全写入流程。
- 验收：仅负责人从处理中请求补充；仅提交人有效补充；正文或附件至少一个；补充或撤回后回处理中且原负责人不变；转交不重算截止时间。
- 测试：状态/关系权限参数化测试；附件故障回滚；补充、撤回、转交和撤销并发冲突；UTC 截止时间单测。
- 完成定义：每次期限产生和失效都有记录；不能在待补充直接提交解决结果。
- Git 检查点：补充循环集成测试通过后提交 `feat: implement requester supplement loop`。

### TASK-032：实现解决、确认、退回、撤销与关闭

- 能力：`CAP-05`。
- 依赖：`TASK-031`。
- 工作：实现 submit-resolution、confirm-resolution、report-unresolved、cancel、close；处理完成方式、关闭方式、关闭原因和重复工单关系。
- 验收：只有负责人提交解决结果；只有提交人确认或退回；退回保留原负责人和旧解决记录；四种非终态可由提交人撤销；异常关闭仅限处理中负责人；三个终态不可重开。
- 测试：全部合法/非法状态转换、角色与资源关系、重复关闭关联、终态保护、同一版本并发确认/退回/撤销/关闭、历史不可变性。
- 完成定义：七种状态和所有人工转换与业务文档一致；结束字段组合满足数据库约束。
- Git 检查点：完整状态机和并发测试通过后提交 `feat: complete manual ticket lifecycle`。

### TASK-033：交付 IT 与员工动作页面

- 能力：`CAP-04`、`CAP-05`。
- 依赖：`TASK-030`～`TASK-032`。
- 工作：扩展 `/tickets` 的公共队列、负责中和参与历史；在详情页按 allowedActions 提供领取、记录、调整、转交、补充、解决、确认、退回、撤销和关闭对话框。
- 验收：按钮随最新快照变化；409 后要求刷新而非自动重放；多角色用户可显式切换 scope；成功动作即时展示新状态和时间线。
- 测试：组件测试覆盖按钮/表单/冲突提示；Playwright 覆盖员工提交→IT 领取→处理→解决→员工确认，以及补充、退回、转交、取消、关闭代表路径。
- 完成定义：所有人工动作均可在最小页面完成；前端不自行推断服务端未返回的权限。
- Git 检查点：核心人工流程 E2E 通过后提交 `feat: deliver interactive ticket workflow`。

M3 阶段验收：人工参与的一张工单可以走完所有 v1 合法路径，权限、并发和历史记录均有自动化证据。

## 10. M4：自动化与跨存储可靠性

目标：补齐无人操作和进程故障路径，使核心业务在重复执行和重启后仍保持一致。

### TASK-040：实现待确认与待补充超时

- 能力：`CAP-06`。
- 依赖：`TASK-032`。
- 工作：实现可重复扫描的内部定时任务；待确认超时自动完成，待补充超时自动关闭；使用状态、截止时间和版本条件更新并记录 SYSTEM 操作者。
- 验收：停机恢复后补处理已到期工单；重复扫描不重复结束；旧期限失效后不能影响新状态；人工与系统动作并发只有一个成功。
- 测试：固定 Clock 单测；真实 MySQL 到期扫描、批次和并发集成测试；两种自动结束记录及完成/关闭方式验证；重复运行测试。
- 完成定义：不暴露管理员手动 HTTP 入口；任务失败可诊断且下次运行可安全重试。
- Git 检查点：时间与并发测试通过后提交 `feat: automate ticket deadlines safely`。

### TASK-041：实现附件清理、对账与完整性诊断

- 能力：`CAP-06`。
- 依赖：`TASK-021`、`TASK-040` 的调度基础。
- 工作：实现过期暂存清理、最终目录孤儿隔离/删除、数据库有记录但文件缺失告警，以及启动时目录/原子移动能力检查。
- 验收：只处理解析后位于配置根目录的随机 storage key；孤儿可清理；元数据存在但文件缺失时不伪造成功、不自动删元数据；清理失败不破坏业务事实。
- 测试：路径穿越、活动暂存保护、进程中断模拟、孤儿/缺失文件、重复扫描、清理异常和同标识并发保护。
- 完成定义：故障日志含 trace/任务阶段但不含真实磁盘路径或附件内容；操作可重复。
- Git 检查点：故障恢复矩阵通过后提交 `feat: reconcile attachment storage`。

M4 阶段验收：系统动作和文件对账可重复运行，人工/自动并发以及跨存储失败均不会制造错误业务成功。

## 11. M5：管理与概览

## 13. 全局完成定义

任一任务只有同时满足以下条件才可标记完成：

1. 实现范围没有越过已确认 v1 边界。
2. API、权限、状态、数据和错误行为与已确认文档一致；必要变更先回到设计确认。
3. 相关自动化测试通过，且失败路径与权限负向路径不缺失。
4. 本地执行了与风险匹配的命令，并记录真实结果；不能以“已提交”代替测试证据。
5. 文档、配置示例和启动方式随实现同步，不包含密钥、密码、Token 或机器绝对路径。
6. `PROJECT_STATUS.md` 在阶段完成、阻塞、交接或关键决策变化时保持同步。
7. 当前主题分支工作区清晰，PR 只包含该主题范围内的变更。

## 14. 开发中的集中确认点

每个里程碑原则上只有两个集中确认点：

1. **开工确认**：说明本里程碑目标、文件范围、关键取舍和验证命令，用户确认后实施。
2. **阶段验收**：汇总实际结果、测试证据、限制和下一里程碑，用户确认后执行分支推送、PR、合并、本地 main 仅快进同步和下一分支创建。

出现以下情况必须提前暂停：

- 需要改变 v1 范围、状态机、权限或数据所有权。
- 需要修改已经在共享环境执行的迁移脚本。
- 需要引入当前技术边界外的基础设施。
- 跨存储顺序、并发条件或安全策略无法按已确认方案实现。
- 测试暴露设计文档之间的实质矛盾。

普通实现细节、命名整理和由确认方案直接推导的低风险内容可以在同一里程碑内连续处理，并在验收点统一说明。
