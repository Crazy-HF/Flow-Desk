# FlowDesk 前端重铸分析：参考 RuoYi-Vue-Plus 页面语言

日期：2026-10-24。状态：**视觉参考与派发指令已补齐；本工作树未实施页面**。

## 1. 目标与本轮边界

**已确认**：用户认为当前页面观感不满足预期，希望前端推倒重铸，以 RuoYi-Vue-Plus 的页面实现风格为参考，后续交给其他 Agent 实施。2026-10-24 用户补充两张目标截图，并提出用户角色分配、角色权限分配先做右侧抽屉样板。本工作树只保存图片和指令，不改页面、接口、后端、测试，也不提交或推送。

**暂时假设**：“采用风格”指借鉴后台的布局、密度、表单/表格/工具栏组织与视觉节奏，保留 FlowDesk 的业务流程和现有 Vue 工程。此假设供后续确认，不把“参考若依风格”解释成迁入若依代码或后端框架。仓库根 `AGENTS.md` 仍明确写着“原生开发，不使用若依”；若用户要直接替换前端工程，这条约束需先明确更新。

成功应由页面实际截图与任务完成效率判断，而不是“代码已换皮”。主要受众是员工、IT 支持和管理员；重铸后仍要一眼看清工单状态、责任人、下一步动作。

## 2. 参考对象与证据边界

- [RuoYi-Vue-Plus 主仓库](https://github.com/dromara/RuoYi-Vue-Plus/blob/6.X/README.md) 指向官方 Vue + Element Plus 前端 [plus-ui 的 `6.X-Vue` 分支](https://github.com/CrazyLionCat/plus-ui/tree/6.X-Vue)；其 README 与 [package.json](https://github.com/CrazyLionCat/plus-ui/blob/6.X-Vue/package.json) 显示 Vue 3、TypeScript、Vite、Element Plus。它还带多租户、动态菜单、字典、生成器、VXE 表格、UnoCSS 等能力，不能把这些能力当作纯视觉样式引入。
- 用户已提供两张其认可的 RuoYi-Vue-Plus 界面截图，作为**本次视觉目标的优先真源**：`.ui-craft/references/06-ruoyi-plus-home-user-reference.png`（首页/壳层）与 `.ui-craft/references/07-ruoyi-plus-user-list-user-reference.png`（用户管理）。截图展示了实际目标构图，但未附页面版本或 commit；实施 Agent 无需为这两张图再寻找替代物，若研究官方源码则另行记录版本与来源。
- 本地五张既有参考已逐张查看：`.ui-craft/references/01`、`02` 是用户曾认可的管理后台列表；`03` 是用户明确不满意的旧 FlowDesk；`04`、`05` 是工单列表与详情参考。这些图片**不是** RuoYi-Vue-Plus 官方截图，不能混称。旧认可只说明当时的偏好，2026-10-24“推倒重铸”的新反馈优先。

## 3. 当前代码事实

| 位置 | 现状 | 对重铸的含义 |
| --- | --- | --- |
| `frontend/package.json` | Vue 3.5、Element Plus 2.14、Vite 8、Pinia、Vue Router，已有 Vitest / Playwright | 与参考项目的基础栈接近，无需为页面风格换框架 |
| `src/layout/index.vue`、`AppHeader.vue`、`AppSidebar.vue`、`AppBreadcrumb.vue` | 顶栏、侧栏、面包屑、工作区已分离；小屏抽屉；侧栏入口由本地权限常量过滤 | 可重铸壳层，保留路由和授权语义；目前侧栏几乎纯文字，层级辨识度依赖间距与颜色 |
| `AppPage.vue`、`main.css` | 列表页用全宽工作区，普通页仍走居中卡片；`main.css` 承担大量共享样式 | 需先统一页面容器及密度规则，否则单页改版会不断产生特例 |
| `tokens.css`、`element/var-override.scss` | token 与 Element Plus 主题分工明确，Stylelint 限制硬编码 | 视觉变更应从 token 与主题映射开始，不能逐页覆写组件内部结构 |
| `views/admin/*` | 用户、角色、权限、授权、分类等管理页；列表已有筛选、工具栏、数据区和分页 | 结构已部分接近后台列表；重铸要解决整体比例、排版与操作密度，避免只换主色 |
| `views/work/*` | 工单列表/队列、创建、详情、通知、概览、AI 辅助；业务状态与动作复杂 | 不能照搬通用 CRUD 页；工单详情必须保留时间线、责任关系、附件和动态动作 |
| `api/http.ts`、`stores/auth`、`constants/authorization.ts` | Access Token 在内存，Refresh 用 HttpOnly Cookie，前端入口按权限显示 | 任何壳层替换都不得改变认证、刷新与后端最终授权边界 |

旧 `.ui-craft/frontend-redesign-handoff.md` 与 `frontend/PAGE-TEMPLATE.md` 规定了管理列表骨架、六态、token、截图要求。它们属于**现行实现规范**；用户新提供的 `06`/`07` 图片优先于其中旧的视觉参考，安全/可用性硬规则继续有效。实施时列出要废止的旧视觉规定并同步文档，不能让 Agent 同时遵守互相矛盾的两套视觉要求。

当前工作树位于 `flow-desk/ai-ticket-assistant-analysis`，存在 AI 主题的未提交改动，并有未跟踪 `.ui-craft/`。后续实现须先重新核对 Git 状态；不要为视觉任务清理、暂存或覆盖这些文件，也不要在 AI 主题分支上叠加整轮前端改版。

## 4. 三种路径与建议

| 路径 | 做法 | 收益 | 代价/风险 |
| --- | --- | --- | --- |
| A. 只调 token 和 CSS | 保持所有页面 DOM，改色、间距、阴影、字号 | 快，回归范围小 | 解决不了页面信息架构与视觉节奏，容易再次变成“安全但平淡” |
| **B. 保留工程，重铸壳层与页面模板（建议）** | 用官方 6.X 页面作视觉参照，重新定义导航、页头、筛选/工具栏/表格、详情与表单布局；按业务页逐批替换 | 可形成统一后台感，保住现有 API、权限、测试资产 | 要做跨页面设计决定与逐批真实渲染验收 |
| C. 迁入 plus-ui 前端工程 | 在官方工程里重新接 FlowDesk 路由、认证、API 和业务页 | 可直接得到其完整壳层与组件体系 | 迁移面极大；官方多租户/动态菜单/权限模型与 FlowDesk 不同，也触及“原生开发，不使用若依”的项目约束 |

建议选 B。它和用户说的“页面实现风格”最贴近；若实际意图是 C，应先单独确认并重估工程、授权与维护成本。

## 5. 建议的目标页面语言（待视觉定稿）

1. **应用壳**：按 `06`/`07` 采用深海军蓝侧栏（不是纯黑）、图标加文字的分组导航、蓝色选中态、浅灰工作区、白色圆角顶栏；顶部面包屑/全局操作与下一行的页面标签带形成两层。只显示 FlowDesk 真实路由与真实可用的全局操作；标签带若实现，必须能正确切换/关闭且不破坏浏览器历史，不能摆假标签。当前禁用搜索位不能被画成可用搜索。
2. **管理列表**：按 `07` 采用占满工作区的独立筛选面板与数据面板；筛选面板有标题与收起态，数据面板把标题/记录说明/动作栏、表格、分页组成一体。保持输入与按钮尺度、轻描边、适中留白、表头和行高的层级。`01`、`02` 是历史辅助参考，`07` 优先。
3. **工单列表/队列**：保留“工作范围”先于普通筛选的语义。标题、编号、状态、优先级、负责人、更新时间形成明确扫描顺序；不为模仿 CRUD 表格而丢掉范围切换、待我批准等真实能力。
4. **工单详情**：头部突出编号、标题、状态和当前可执行动作；主栏放描述、处理记录、补充往返、附件和关联；次栏放类别、优先级、人员与时间。按钮继续由服务端 `allowedActions` 与前端权限共同收口，动作后刷新版本与时间线。
5. **角色/权限分配抽屉样板**：用户角色分配从用户行入口打开右侧抽屉，角色权限分配从角色行入口打开右侧抽屉；主体、可选项、当前授权、保存/取消/错误/加载按已有接口契约显示。先以抽屉样板让用户看效果，保留原有两条授权路由与深链入口，用户认可后再决定是否统一改成抽屉。概览不凭空增加图表或指标。
6. **窄屏**：导航改抽屉；筛选折叠或换行；表格允许局部横向滚动并保留关键列与操作；详情次栏下移。禁止整页横向溢出。

每类页面做一个可点击的视觉样板，再推广。样板需包含正常、加载、空、错误、禁用、无权限和窄屏状态；只展示一张静态满数据截图不足以验收。

## 6. 实施拆分与交接边界

1. **视觉基线与样板**：直接使用用户给的 `06`/`07` 两张图作为壳层/用户列表主参考，截取当前 FlowDesk 同视口页面，做差异表；先做壳层 + 用户列表 + 两个分配抽屉样板，另做工单详情同语言适配。用户集中看一次实际截图与交互，不逐页反复确认。
2. **设计系统与壳层**：确定色板、字体、空间、圆角、表格/表单尺度；更新 `tokens.css`、Element Plus 映射和壳层组件，检查登录、403、404、抽屉、通知及账号菜单。
3. **列表模板**：先用户管理页，再角色/权限/授权/分类；复用共享列表骨架。只改视觉和必要组件结构，不改 API 参数、批量能力或权限规则。
4. **工单主链路**：列表/队列 → 详情 → 新建 → 通知/首页/概览/AI 面板。详情单独安排回归，因为动作最多、版本与状态耦合最强。
5. **收口**：逐页更新 `frontend/AGENTS.md`、`frontend/PAGE-TEMPLATE.md`、`.ui-craft/brief.md` 等已被新视觉取代的规定；留截图、差异记录与测试证据。仓库要求的状态文档在实施阶段切换时再更新。

可按“壳层与样板”“管理端”“工单端”“其余页面”拆成独立短期分支/主题，避免一次巨型提交。每批从当时最新 `main` 开始，处理跨批共享样式冲突；不得假设当前 AI 分支可直接充当基线。

## 7. 不得破坏的契约

- FlowDesk 保持自己的品牌、导航名称、路由、接口模型、权限码和错误码；不添加官方项目里的部门、岗位、多租户、字典、导出、动态菜单、代码生成或不存在的批量功能。
- `frontend/AGENTS.md` 的 token 唯一真源、六态、可访问性、错误码映射、表格列宽规则继续有效，除非后续明确修订视觉条款。
- Access Token 仍只在 Pinia 内存；Refresh Cookie、401 协调和后端最终鉴权不变。
- 工单详情保持服务端 `allowedActions`、`version` 乐观锁回写、404 不泄漏、处理记录顺序及附件授权代理；管理员交接与受保护角色入口需完整保留。
- 引用官方代码或素材前核对其具体许可证与署名要求；单纯模仿布局不等于复制代码。官方 plus-ui 声明 MIT，落地 Agent 仍需检查拟复制文件的许可头及依赖许可。

## 8. 验收标准与证据

| 维度 | 最低可检查结果 |
| --- | --- |
| 视觉 | 1440×900、1920×1080、375×812 实际截图；优先与用户给的 `06`/`07` 图片及旧 FlowDesk 截图逐项比较导航、首屏信息层级、密度、控件、表格、弹窗；记录偏差与修正。不得仅写“更像若依” |
| 功能 | 员工提交与查询、IT 领取/处理/转交/结束、管理员管理与交接、通知跳转等现有主链路可操作；禁用搜索仍明确禁用 |
| 状态与权限 | 每类样板覆盖正常、加载、空、错误、禁用、无权限、窄屏；权限不足不能通过隐藏按钮伪装安全 |
| 工程 | 在 `frontend/` 跑 `pnpm typecheck`、`pnpm lint`、`pnpm build`、受影响单测与 E2E；真实栈条件不满足时如实列未跑项 |
| 交付 | 每批列出改动范围、参照截图、实现截图、Before/After/Why、通过/失败/未运行检查及未解决偏差；保留与该批无关的工作树改动 |

## 9. 待用户一次确认的决定

1. **视觉主参考已确定**：用户给的 `06`/`07` 两张图；其余页面按同一视觉语言外推。后续可补更多截图，但不作为启动样板的前置条件。
2. **重铸范围**：按登录后的业务区先行；登录与错误页只检查协调性，是否重做这些页面留到样板反馈后决定。
3. **迁移层级已定为路径 B**：只采用视觉与交互语言，保留 FlowDesk 前端工程；若以后改为整套迁移，需先修订仓库“不使用若依”的约束并另立方案。
4. **新增壳层能力**：截图里的页面标签带已进入视觉目标，但 Agent 应先用现有路由做可用且最小的标签切换样板；布局设置、暗色模式、全局搜索等其他能力不做。若标签带实现复杂度或浏览器历史行为有冲突，在样板报告中给出具体证据与取舍。

以上默认决定足以启动样板。样板展示并经用户集中确认后，再推广全站。
