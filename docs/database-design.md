# FlowDesk 数据库设计

## 1. 阶段目标与边界

**已确认**：数据库设计先完成逻辑数据模型，再设计 MySQL 物理表、字段类型、约束和索引。

当前文档状态：逻辑数据模型和 MySQL 物理模型均已确认，数据库设计状态为 **Ready**。

本文档只回答以下问题：

- 哪些业务事实需要持久化，以及各实体如何关联。
- 当前状态、不可变历史、权限查询、超时扫描和并发更新依赖哪些数据。
- 已确认逻辑实体如何映射为 MySQL 表、字段、约束和索引。

本文档不生成建表 SQL、迁移脚本或 API，也不实际创建数据库。

## 2. 逻辑模型原则

1. MySQL 是持久业务事实的唯一权威来源。
2. 工单保存当前快照，工单记录保存不可变历史；状态变化时二者必须在同一事务中更新。
3. 身份授权采用完整 RBAC 关系，但 v1 的角色、权限及角色权限映射由系统预置，不开放在线编辑。
4. RBAC 只判断用户是否具有某类能力；工单归属、参与关系、当前负责人和状态仍由业务规则校验。
5. 工单状态、优先级、记录类型、完成方式和关闭原因是固定业务枚举，不建立可在线维护的字典实体。
6. 当前有效期限保存在工单快照中，定时任务扫描工单，不建立独立任务实体。
7. 文件内容不进入 MySQL；MySQL 只保存附件元数据及业务归属。

## 4. 身份与访问实体

### 4.1 用户

用户代表能够登录 FlowDesk 的企业内部人员。

逻辑信息包括：系统标识、登录标识、显示名称、密码安全摘要、启用状态、创建与更新时间。账号停用后不能登录或执行新操作，但用户及其历史引用不能删除。

### 4.2 角色

角色代表职责集合。v1 预置普通员工、IT 支持人员和系统管理员三个稳定角色编码，不允许在线新增、删除或改变角色含义。

### 4.3 权限

权限代表后端可校验的业务能力，例如用户管理、分类管理、创建工单、领取工单和处理工单。权限编码保持稳定，不使用页面路径、按钮名称或前端菜单作为权限标识。

### 4.4 用户角色

用户角色表达用户与角色的多对多关系。一个用户至少拥有一个角色，可以同时拥有多个角色；同一用户不能重复拥有同一角色。

角色分配变化必须触发现有登录会话失效。移除 IT 支持人员角色或停用账号前，必须先完成其活动工单的管理性交接。

### 4.5 角色权限

角色权限表达角色与权限的多对多关系。v1 由系统预置并随版本迁移维护，不提供运行时编辑入口。

系统管理员角色本身不包含查看具体工单内容的权限；多角色用户的权限取角色并集，但仍必须通过工单级业务校验。

## 5. 分类实体

### 5.1 工单分类

工单分类保存稳定标识、唯一名称、启用状态以及必要的展示顺序。分类是单级结构，不具有父分类。

已被工单引用的分类不能删除，只能停用；停用分类不能用于新工单或分类调整，但历史工单继续引用并显示它。未被任何工单引用的分类才允许删除。

## 6. 工单实体

### 6.1 工单当前快照

工单保存当前查询和业务校验直接需要的信息：

- 系统标识与唯一业务编号。
- 唯一提交人和提交时间。
- 不可覆盖的原始标题与问题描述。
- 当前分类和当前优先级。
- 当前状态。
- 当前负责人；进入终态后作为最后负责人保留。
- 当前有效的补充截止时间或确认截止时间。
- 提交人生成的创建防重键，用于识别同一次工单提交重试。
- 适用时的完成方式、关闭方式、结束原因和结束时间。
- 创建时间、最近更新时间和乐观并发版本。

快照用于列表、权限校验、超时扫描和数据概览，不代替不可变历史记录。

状态与负责人约束：

- 待受理没有负责人。
- 处理中、待补充和待确认必须有负责人。
- 负责人必须是启用且拥有 IT 支持人员角色的用户，并且不能是该工单提交人。
- 已完成、已取消和已关闭是不可重开的终态。

期限约束：

- 待补充只有补充截止时间有效。
- 待确认只有确认截止时间有效。
- 其他状态没有有效的补充或确认截止时间。

### 6.2 工单记录

工单记录是按发生顺序追加的不可变业务事实。每张工单至少具有一条创建记录；已有记录不能覆盖或删除，修正必须产生新记录。

所有记录共享的逻辑信息包括：所属工单、记录类型、工单内顺序、执行者类型、执行用户、发生时间以及该记录要求的正文或原因。系统自动操作的执行者类型为系统，执行用户为空。

不同记录按类型保存必要的结构化上下文：

| 记录类型 | 必须表达的关键事实 |
| --- | --- |
| 创建 | 初始标题、描述、分类、优先级和提交人 |
| 领取 | 新负责人 |
| 处理 | 当前负责人的处理正文 |
| 分类调整 | 原分类、新分类和原因 |
| 优先级调整 | 原优先级、新优先级和原因 |
| 转交 | 原负责人、新负责人和原因 |
| 管理性交接 | 原负责人、新负责人、管理员和原因 |
| 补充请求 | 请求正文和补充截止时间 |
| 员工补充 | 补充正文或附件 |
| 撤回补充请求 | 撤回原因 |
| 解决结果 | 处理结论和确认截止时间 |
| 未解决反馈 | 员工反馈原因 |
| 完成 | 员工确认或系统超时完成方式 |
| 取消 | 员工撤销原因 |
| 关闭 | 手动或自动关闭方式、标准原因和具体说明 |

工单快照变化与对应记录必须共同成功或共同失败，不能出现状态已改变但记录缺失，或记录已生成但状态未改变。

### 6.3 工单附件

工单附件保存所属记录、系统存储标识、原始文件名、媒体类型、文件大小、完整性摘要、上传人和上传时间。

附件只能属于创建记录或员工补充记录，一份附件只能属于一个记录。附件内容保存在后端控制的本地持久化目录，访问权限从所属记录和工单继承。

### 6.4 工单关联

工单关联保存来源工单、目标工单、关联类型、创建人和创建时间，是有方向的关系。

v1 只允许：

- 后续工单引用：新工单指向提交人有权查看的原工单。
- 重复工单指向：被关闭工单指向同一提交人的另一张有效工单。

来源和目标不能相同；同一来源工单的同一关联类型最多存在一个目标；多张来源工单可以指向同一目标。关联不会合并两张工单的生命周期，也不会授予额外访问权限。

### 6.5 工单参与者

工单参与者表示某名 IT 支持人员曾经成为该工单负责人。领取、业务转交或管理性交接产生新负责人时，在同一事务内确保该参与关系存在。

同一工单与同一用户最多一条参与关系；关系一旦产生不删除。它不表示当前负责人，当前责任仍以工单快照为准。

设置该实体是为了直接、稳定地校验历史参与者的工单查看权限，避免每次授权都扫描不同类型的历史记录。执行管理性交接的系统管理员不会因此成为工单参与者。

## 7. 核心数量关系

| 来源 | 关系 | 目标 | 数量与约束 |
| --- | --- | --- | --- |
| 用户 | 拥有 | 角色 | 多对多；每个用户至少一个角色 |
| 角色 | 包含 | 权限 | 多对多；v1 映射由系统预置 |
| 用户 | 提交 | 工单 | 一对多；每张工单恰好一个提交人 |
| 用户 | 当前负责 | 工单 | 一对多；每张活动工单最多一个负责人 |
| 工单分类 | 被引用 | 工单 | 一对多；每张工单恰好一个当前分类 |
| 工单 | 包含 | 工单记录 | 一对多；每张工单至少一条创建记录 |
| 工单记录 | 携带 | 工单附件 | 一对多；仅创建和员工补充记录允许携带 |
| 工单 | 关联 | 工单 | 有向自关联；按来源和类型限制唯一目标 |
| 工单 | 具有 | 工单参与者 | 一对多；同一工单与用户组合唯一 |

## 8. 权限查询所需数据

后端授权需要同时使用 RBAC 和工单关系：

- 普通员工通过工单提交人关系查看自己的工单。
- IT 支持人员可以查看公共待受理工单。
- 当前负责人通过工单快照获得处理权限。
- 历史负责人通过工单参与者关系获得后续查看权限，但不能继续执行当前负责人操作。
- 系统管理员默认不能查看工单正文、记录或附件；管理性交接只读取必要元数据。
- 附件和工单关联不能扩大用户对所属工单或目标工单的访问范围。

## 9. 超时与并发所需数据

### 9.1 超时扫描

- 待确认扫描使用当前状态和确认截止时间，成功后写入系统超时完成记录。
- 待补充扫描使用当前状态和补充截止时间，成功后写入系统自动关闭记录。
- 转交待补充工单不改变补充截止时间。
- 状态已变化或期限已失效的工单不得被重复处理。

### 9.2 并发控制

每个状态或负责人变更都同时校验预期状态、预期负责人和工单版本。更新成功后，在同一事务中更新快照、追加记录，并在需要时增加工单参与者。

管理性交接涉及多张活动工单时，全部负责人替换、参与关系、交接记录以及用户账号或角色变化必须共同成功或共同失败。

## 10. 存储边界

| 数据 | 权威存储 |
| --- | --- |
| 用户、RBAC、分类、工单、记录、参与者、附件元数据和工单关联 | MySQL |
| JWT 登录会话、Refresh Token 摘要、会话状态和撤销信息 | Redis |
| 附件文件内容 | 后端控制的本地持久化目录 |

Redis 会话和本地附件内容属于总体数据设计，但不转换为 MySQL 业务实体。

## 11. 不建立的逻辑实体

v1 暂不建立以下实体：

- 前端菜单及菜单权限。
- 可在线编辑的角色、权限配置版本。
- 状态、优先级和记录类型字典。
- SLA、催办、升级或外部通知任务。
- 独立的超时任务或任务队列表。
- 多租户、组织部门、IT 支持小组或外部供应商。
- 独立报表库或统计快照。

## 12. 逻辑完整性约束

1. 用户账号不物理删除，且始终至少拥有一个角色。
2. 系统中始终至少存在一个启用的系统管理员。
3. 用户、角色和权限编码在各自范围内唯一。
4. 分类名称唯一；已被工单引用的分类不能删除。
5. 工单编号唯一，提交人和原始问题信息提交后不可更换或覆盖。
6. 工单任一时刻只有一个状态，并满足对应负责人和期限约束。
7. 当前或最后负责人不能是工单提交人。
8. 工单记录只追加不覆盖，并在所属工单内保持确定顺序。
9. 附件必须属于允许携带附件的工单记录。
10. 工单关联不能指向自身，且必须满足关联类型对应的可见性和同提交人约束。
11. 工单参与者只能由曾经成为负责人的 IT 支持人员产生，不能借此授予管理员正文访问权。
12. 快照、历史记录、参与关系和必要关联在同一业务事务中保持一致。
13. 互斥状态或负责人操作并发发生时只能有一个成功。

## 13. 逻辑模型确认结论

**已确认**：逻辑数据模型采用以下方案：

1. 采用完整 RBAC 五实体关系，但角色、权限和映射在 v1 中预置且不可在线编辑。
2. 工单采用“当前快照 + 不可变记录”双模型，并在同一事务中保持一致。
3. 增加工单参与者实体，持久化曾经担任负责人的 IT 人员，以直接支持历史参与权限查询。
4. 当前补充或确认期限保存在工单快照中，不建立独立超时任务实体。
5. 工单关联使用独立有向实体；同一来源和关联类型最多一个目标。
6. 状态、优先级、记录类型和结束原因使用固定枚举，不建设可编辑字典。

## 14. 逻辑模型验收结论

**已确认**：逻辑数据模型已经通过以下验收检查：

- 需要持久化的核心实体及职责明确。
- 用户、RBAC、分类、工单、记录、附件、关联和参与者之间的数量关系明确。
- 工单当前快照与不可变历史记录的职责边界明确。
- 权限查询、超时扫描和乐观并发所需的逻辑数据明确。
- 逻辑完整性约束与业务模型和总体架构一致。
- 尚未提前确定 MySQL 字段类型、索引、建表 SQL、迁移脚本或 API。

## 15. MySQL 物理模型基线

**已确认**：物理模型采用以下统一约定：

- 数据库版本以 MySQL 8.4 LTS 为基线，存储引擎使用 InnoDB。
- 默认字符集使用 `utf8mb4`，排序规则采用 MySQL 8.4 对应的 Unicode 不区分大小写规则。
- 内部主键使用无符号自增 `BIGINT`；对外展示的工单编号单独设置唯一约束。
- 时间使用毫秒精度 `DATETIME(3)` 并统一保存 UTC，展示时由应用转换时区。
- 固定业务枚举使用字符串编码和 `CHECK` 约束，不使用 MySQL `ENUM`。
- 核心关系使用外键保护，不依赖应用代码单独维持引用完整性。
- 不设置全局软删除字段；用户和分类使用明确状态，工单及历史数据禁止删除。
- 工单记录使用结构化字段保存核心事实，不把关键业务数据整体放入 JSON。

除密码摘要、正文、文件名等确有需要的内容外，字符串长度应保持明确上限。所有表名和字段名使用小写蛇形命名。

## 17. 身份与访问表

### 17.1 `iam_user`

| 字段 | 建议类型 | 空值 | 约束与含义 |
| --- | --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 否 | 主键，自增 |
| `username` | `VARCHAR(64)` | 否 | 登录名，唯一且按不区分大小写规则比较 |
| `display_name` | `VARCHAR(100)` | 否 | 页面展示名称 |
| `password_hash` | `VARCHAR(255)` | 否 | 密码安全摘要，不保存明文 |
| `status` | `VARCHAR(16)` | 否 | `ENABLED`、`DISABLED` |
| `created_at` | `DATETIME(3)` | 否 | UTC 创建时间 |
| `updated_at` | `DATETIME(3)` | 否 | UTC 最近更新时间 |
| `version` | `BIGINT UNSIGNED` | 否 | 账号和角色管理的乐观版本，初始为 0 |

约束与索引：

- 主键：`id`。
- 唯一约束：`username`。
- 检查约束：`status` 只能是已定义值。
- 普通索引：`status`，用于选择可登录用户、有效 IT 人员和管理员保护检查。

用户不允许物理删除。至少一个角色、最后启用管理员保护及活动工单交接属于跨表事务约束。

### 17.2 `iam_role`

| 字段 | 建议类型 | 空值 | 约束与含义 |
| --- | --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 否 | 主键，自增 |
| `code` | `VARCHAR(50)` | 否 | 稳定角色编码 |
| `name` | `VARCHAR(50)` | 否 | 展示名称 |
| `description` | `VARCHAR(255)` | 是 | 角色说明 |
| `created_at` | `DATETIME(3)` | 否 | UTC 创建时间 |

`code` 唯一。v1 角色由迁移脚本预置，不提供在线新增、修改或删除。

### 17.3 `iam_permission`

| 字段 | 建议类型 | 空值 | 约束与含义 |
| --- | --- | --- | --- |

## 19. 工单核心表

### 19.1 `ticket`

| 字段 | 建议类型 | 空值 | 约束与含义 |
| --- | --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 否 | 主键，自增 |
| `ticket_no` | `VARCHAR(32)` | 否 | 对外业务编号，唯一 |
| `submission_key` | `CHAR(36)` | 否 | 提交端生成的 UUID，与提交人组合后保证创建幂等 |
| `requester_id` | `BIGINT UNSIGNED` | 否 | 外键指向提交人 |
| `title` | `VARCHAR(200)` | 否 | 原始标题，提交后不可覆盖 |
| `description` | `TEXT` | 否 | 原始问题描述，提交后不可覆盖 |
| `category_id` | `BIGINT UNSIGNED` | 否 | 当前分类外键 |
| `priority` | `VARCHAR(16)` | 否 | `LOW`、`MEDIUM`、`HIGH` |
| `status` | `VARCHAR(32)` | 否 | 七种工单状态编码 |
| `assignee_id` | `BIGINT UNSIGNED` | 是 | 当前负责人；终态时作为最后负责人保留 |
| `action_deadline_at` | `DATETIME(3)` | 是 | 待补充或待确认的当前有效截止时间 |
| `completion_method` | `VARCHAR(32)` | 是 | 员工确认或系统超时完成 |
| `close_method` | `VARCHAR(16)` | 是 | 手动关闭或系统自动关闭 |
| `close_reason` | `VARCHAR(32)` | 是 | 关闭标准原因 |
| `ended_at` | `DATETIME(3)` | 是 | 进入终态的 UTC 时间 |
| `record_seq` | `INT UNSIGNED` | 否 | 当前最大工单内记录序号；创建事务写入首条记录后为 1 |
| `version` | `BIGINT UNSIGNED` | 否 | 工单乐观版本，初始为 0 |
| `created_at` | `DATETIME(3)` | 否 | UTC 创建时间 |
| `updated_at` | `DATETIME(3)` | 否 | UTC 最近更新时间 |

业务编码建议由 `FD-`、创建日期和内部自增标识组成，例如 `FD-20260907-000001`。内部关联始终使用 `id`，不使用可展示编号作为外键。

主要唯一约束、外键和索引：

- 唯一约束：`ticket_no`、`(requester_id, submission_key)`。
- 外键：`requester_id`、`assignee_id` 指向 `iam_user.id`，`category_id` 指向 `ticket_category.id`，均限制删除。
- 员工列表：`(requester_id, created_at, id)`。
- 公共队列和状态筛选：`(status, priority, created_at, id)`。
- 负责人工作台：`(assignee_id, status, updated_at, id)`。
- 超时扫描：`(status, action_deadline_at, id)`。
- 分类概览：`(category_id, status)`。

物理检查约束至少覆盖：

- `priority`、`status`、完成方式、关闭方式和关闭原因的合法编码。
- 待受理时负责人为空；处理中、待补充、待确认、已完成和已关闭时负责人非空；已取消可以为空。
- 负责人存在时不能等于提交人。
- 待补充或待确认时截止时间非空，其他状态截止时间为空。
- 非终态的 `ended_at` 为空，三个终态的 `ended_at` 非空。
- 仅已完成状态允许且要求完成方式；仅已关闭状态允许且要求关闭方式和关闭原因。
- 系统自动关闭只能使用“逾期未补充信息”，IT 手动关闭只能使用重复、不属于 IT 范围或无效三种原因。

负责人是否具有有效 IT 角色、分类是否启用、重复工单目标是否合法等跨表规则由事务用例校验，不能仅靠单表 `CHECK` 完成。

## 22. 外键与删除策略

- 用户、角色、权限、工单、工单记录和被引用分类均禁止通过级联删除清理历史。
- 所有核心外键默认采用限制删除。
- 用户角色关系的移除是显式授权操作，不依赖删除用户级联清理。
- 角色权限映射由迁移脚本显式维护。
- 工单、记录、附件元数据、参与者和关联不提供业务删除操作。
- 未被工单引用的分类可以显式物理删除；存在引用时由外键拒绝。
- 本地附件文件的创建失败补偿、孤儿文件清理和数据库提交顺序在工程准备阶段设计，不能使用数据库级联替代文件生命周期处理。

## 24. 物理模型事务不变量

以下规则不能只靠单条外键或检查约束，需要由应用事务和条件更新共同保证：

1. 用户始终至少拥有一个角色，系统始终至少有一个启用的系统管理员。
2. 停用账号或移除 IT 角色前，所有活动工单完成原子管理性交接。
3. 当前负责人是启用的 IT 用户，且不是工单提交人。
4. 领取、转交、处理、结束和超时操作同时校验预期状态、负责人和版本。
5. 工单快照、记录序号、不可变记录及参与关系在同一事务内写入。
6. 分类或优先级调整只能使用符合业务规则的目标值并生成对应记录。
7. 重复关闭必须在同一事务中写入关闭记录和合法的重复工单关联。
8. 附件所属记录类型、上传人和工单权限必须在保存元数据前校验。
9. 定时扫描可以重复运行，但只有状态、截止时间和版本仍匹配的工单能够更新成功。
10. 同一提交人使用相同 `submission_key` 重试创建时返回首次创建结果，不生成第二张工单。

## 25. 物理模型验收结论

**已确认**：2026-09-07，以下物理模型设计通过集中验收：

1. 11 张表是否完整覆盖已确认逻辑实体，且没有无业务依据的表。
2. 工单使用一个 `action_deadline_at` 表达当前唯一有效期限是否合适。
3. 工单记录采用单表结构化可空字段，而不是 JSON 或多种记录子表，是否接受。
4. 自增内部主键与独立工单业务编号的职责是否清晰。
5. 外键限制删除、无全局软删除和不可变历史策略是否符合预期。
6. 索引是否都能对应已经确认的列表、权限、超时或统计查询。

API 契约设计阶段确认了创建幂等要求，已同步增加 `submission_key` 及其组合唯一约束，不改变表数量和既有业务模型。

本阶段只形成设计依据，尚未生成建表 SQL、迁移脚本或实际数据库。数据库迁移及种子数据的工程化方案在工程准备阶段确定。
