# FlowDesk 技术架构设计

## 1. 阶段目标与边界

本阶段依据 `docs/kickoff.md` 和 `docs/business-model.md` 中已经确认的业务规则，确定 v1 的系统形态、模块职责、核心技术机制和运行边界。

当前状态：总体架构设计已完成。

本阶段不输出具体数据库表、字段、索引、接口路径、请求响应结构或业务代码。上述内容分别在数据库设计、API 设计和开发阶段完成。

## 2. 架构驱动因素

FlowDesk v1 的架构需要优先满足以下要求：

- 由一名开发者与 Codex 协作完成，结构应便于理解、测试和展示。
- 支撑员工、IT 支持人员和系统管理员三类角色及多角色组合。
- 工单状态、当前负责人和历史记录必须保持一致。
- 领取、转交、结束和超时操作存在并发冲突，必须保证只有一个操作成功。
- 工单正文和附件需要执行相同的服务端权限检查。
- 待确认与待补充超时任务必须可重复执行，并能在停机恢复后补处理。
- v1 以单企业内部系统为边界，不需要多租户、微服务、消息队列或复杂弹性伸缩。
- 项目需要具有清晰、可重复的本地启动、自动化测试和演示方式。

## 3. 系统形态

### 3.1 推荐方案

**已确认**：v1 采用“前后端分离的模块化单体”。

- 后端是一个 Spring Boot 应用和一个部署单元。
- 前端是一个 Vue 3 单页应用，通过 HTTP API 调用后端。
- 后端内部按照业务能力划分模块，但模块运行在同一进程，并共享一个 MySQL 数据库。
- v1 只运行一个后端实例，不引入服务注册、配置中心、API 网关、消息队列或分布式事务。

选择该方案的原因：

- 单体事务能够直接保护工单状态、负责人和记录的一致性。
- 部署与调试成本适合个人学习项目。
- 按业务模块组织代码，仍可展示清晰边界并避免所有代码堆在传统横向分层中。
- 相比微服务，减少网络调用、分布式一致性、链路追踪和多服务部署负担。

主要取舍：前后端需要分别构建；单个应用的扩展粒度不如微服务，但符合 v1 的规模和非目标。

### 3.2 逻辑结构

```text
Vue 3 SPA
    |
    | HTTP / JSON
    v
Spring Boot 模块化单体
    |- 身份与访问
    |- 工单流程（含附件）
    |- 分类配置
    |- 系统管理
    |- 数据概览
    |- 定时任务
    |
    +---- MySQL（业务事实）
    +---- Redis（Token 会话与撤销状态）
    +---- 文件目录（附件内容）
```

## 4. 后端模块边界

**已确认**：后端按业务能力组织为以下模块。

| 模块 | 主要职责 | 不负责的内容 |
| --- | --- | --- |
| 身份与访问 | 用户、角色、账号状态、登录会话和角色级权限 | 工单状态及工单级访问权限 |
| 工单流程 | 工单生命周期、负责人、记录、补充、解决、结束、关联，以及附件元数据、存取和访问权限 | 用户和分类配置维护 |
| 分类配置 | 单级分类的创建、重命名、启用和停用 | 工单处理流程和分类使用情况判断 |
| 系统管理 | 编排账号停用、角色移除、管理性交接和分类删除等跨模块管理用例 | 持有工单、用户或分类业务数据 |
| 数据概览 | 按权限范围统计状态、优先级、分类和负责人数量 | 修改业务数据 |
| 定时任务 | 触发到期工单的自动完成与自动关闭 | 复制工单业务规则 |

模块协作原则：

- 工单流程模块是工单状态变化的唯一入口。
- 定时任务只触发工单流程模块提供的业务操作，不自行更新工单数据。
- 附件作为工单的组成部分，由工单流程模块统一校验业务归属和访问权限，不能仅凭文件地址返回内容。
- 数据概览是只读能力，查询范围必须复用工单权限规则。
- 系统管理模块可以编排身份与访问、工单流程和分类配置模块，但这些模块不能反向依赖系统管理模块。
- 工单流程模块只通过只读接口查询有效用户、角色和分类，不直接修改身份与分类数据。
- 模块间通过明确的应用服务调用，不允许跨模块直接修改对方数据。
- 模块依赖必须保持单向，不允许为了复用代码形成循环依赖。

## 5. 代码组织方式

**已确认**：采用“按业务模块分包，模块内适度分层”的结构。

每个业务模块根据实际需要包含：

- `web`：HTTP 入口、输入格式校验和响应转换。
- `application`：用例编排、事务边界和权限协调。
- `domain`：状态变化、业务规则和核心概念。
- `infrastructure`：数据库、Redis、文件系统及外部技术实现。

不是每个简单模块都必须机械地建立全部目录。公共代码只保存真正跨模块的基础能力，例如统一错误格式、时间来源和当前用户上下文，不建立无边界的 `utils` 包。

该结构比全项目统一的 `controller/service/repository` 横向目录更容易看出业务归属，同时避免为 v1 引入完整六边形架构或复杂领域驱动框架。

## 6. 数据与状态存储

### 6.1 MySQL

**已确认**：MySQL 是所有持久业务事实的唯一权威来源，包括用户、角色、工单、状态、负责人、业务记录、附件元数据和分类。

- 关键状态变化必须在数据库事务内完成。
- 工单当前状态与不可变历史记录在同一次事务中写入。
- 数据概览可以直接查询 MySQL；v1 不建设独立报表库。
- 具体逻辑模型、表结构、约束和索引在下一阶段设计。

### 6.2 Redis

**已确认**：Redis 在 v1 中只保存 JWT 登录会话、Refresh Token 状态和撤销信息，不缓存工单状态、不承担分布式锁，也不作为业务事实来源。

选择该职责边界的原因：

- 账号停用或角色变化后，可以主动使现有 Token 会话失效。
- 短期 Access Token 与可撤销、可轮换的 Refresh Token 分工明确。
- Redis 获得清晰且真实的使用场景，而不是为了技术栈展示强行缓存业务数据。

主要取舍：该方案不是完全无状态的 JWT，每个受保护请求需要确认 Redis 中的会话仍然有效；增加了一次 Redis 访问和 Token 轮换逻辑，但能够实现主动退出、账号停用和角色变化后的立即失效。

### 6.3 附件内容

**已确认**：v1 将附件内容保存在后端控制的本地持久化目录，MySQL 只保存附件元数据和业务归属。

- 上传目录不能作为公开静态目录直接暴露。
- 下载必须经过后端身份、工单权限和附件归属检查。
- 文件名由系统生成，原始文件名仅作为元数据展示。
- 删除业务记录时不能绕过既定的历史保留规则删除附件。
- 文件类型、大小和数量上限在工程准备阶段确定。

本地文件方案适合单实例演示，成本低、行为直观；缺点是后端实例不能随意横向扩容。对象存储属于未来替换方向，不纳入 v1。

## 7. 身份认证与权限

**已确认**：后端使用 Spring Security、JWT、Refresh Token 和 Redis Token 会话实现身份认证。

- 密码只保存安全哈希，不保存或记录明文。
- Access Token 使用短有效期 JWT，前端只保存在内存中，并通过 `Authorization` 请求头发送，不写入 `localStorage`。
- Refresh Token 使用高强度随机值，通过 HttpOnly、Secure、SameSite Cookie 传递；Redis 只保存其安全摘要、会话状态和必要元数据。
- Access Token 携带会话标识；每个受保护请求在验证签名和有效期后，还要确认 Redis 会话仍有效，从而支持立即撤销。
- Refresh Token 每次使用后轮换，旧 Token 立即失效；检测到重复使用时撤销整个登录会话。
- 登录、刷新、退出、账号停用和角色变化需要正确创建、轮换或撤销 Token 会话。
- 使用 Cookie 的刷新接口需要执行 SameSite、来源校验和 CSRF 防护，不能因为 Access Token 使用请求头就忽略刷新端点的 CSRF 风险。
- 前端隐藏按钮只改善体验，所有查看和操作权限必须由后端重新校验。
- 多角色权限按角色组合，但工单内容仍受提交人、当前负责人和历史参与关系限制。
- 管理员执行管理性交接时只能访问必要的工单元数据。

暂不接入企业单点登录、OAuth 身份提供商、短信验证码或第三方账号系统。

## 8. 事务与并发

**已确认**：以 MySQL 事务和乐观并发控制保护工单状态，不使用 Redis 分布式锁。

- 每个改变工单状态或负责人的操作是一个事务用例。
- 更新时同时校验预期状态、预期负责人和数据版本；条件不再满足时返回业务冲突。
- 领取、转交、提交解决结果、员工确认、撤销、关闭和超时处理遵守同一并发策略。
- 业务记录只有在状态变化成功时才写入，不能出现状态失败但记录成功。
- 管理性交接涉及多张活动工单时，账号或角色变化与全部责任交接必须共同成功或共同失败。

乐观控制适合工单系统“读取较多、同一工单写冲突较少”的特点；发生冲突时由用户刷新最新状态，不进行静默覆盖。

## 9. 超时任务

**已确认**：使用 Spring 内置定时任务周期性扫描到期工单，并调用工单流程模块执行条件更新。

- 处理“待确认超过 7×24 小时”和“待补充超过 7×24 小时”两种任务。
- 每次执行只处理到期且状态仍匹配的工单。
- 任务可以重复执行，已经结束或已改变状态的工单不会被重复处理。
- 系统恢复后，周期扫描自然补处理停机期间已经到期的工单。
- v1 单实例运行，不引入分布式任务平台或消息队列。

## 10. 前端边界

**已确认**：前端使用 Vue 3 单页应用，负责页面交互和展示，不复制后端业务规则。

- 使用路由区分登录、员工工单、IT 工作台和系统管理页面。
- 前端状态只用于交互与短期页面数据，MySQL 中的后端状态始终是业务依据。
- 所有状态变化通过后端 API 完成，前端不根据旧页面数据假定操作成功。
- 开发环境通过前端开发服务器代理后端 API，减少跨域和 Cookie 配置差异。

Vue Router、状态管理和组件库等具体依赖在工程准备阶段确认。

## 11. 运行与部署边界

**已确认**：v1 采用单机可重复部署方案。

- 本地开发运行 Vue 开发服务器、一个 Spring Boot 实例、MySQL、Redis 和附件目录。
- 演示部署由 Web 服务器提供前端静态文件，并将 API 请求反向代理到单个后端实例。
- MySQL、Redis 和附件目录需要持久化。
- 使用环境变量或外部配置提供密码、连接信息和文件路径，敏感值不写入仓库。
- 不引入 Kubernetes、服务网格或云厂商专用基础设施。

是否使用 Docker Compose 统一启动依赖，在工程准备阶段决定。

## 12. 测试架构

**已确认**：测试与功能同步建设，采用分层测试组合。

- 领域单元测试：状态机、权限条件、超时判断和业务不变量。
- 应用集成测试：事务、并发冲突、数据库约束和模块协作。
- Web 层测试：认证、授权、输入校验和错误响应。
- 前端测试：关键页面交互和权限展示。
- 端到端测试：覆盖员工提交、IT 领取处理、员工确认及主要异常路径。

具体测试框架、测试数据库和覆盖范围在工程准备阶段确定，但核心业务测试不得推迟到项目末尾补写。

## 13. 明确不采用的方案

v1 不采用以下技术方案：

- 微服务及相关服务治理组件。
- 消息队列和事件总线。
- Redis 业务缓存或分布式锁。
- Elasticsearch 等独立搜索引擎。
- 工作流引擎。
- 对象存储集群。
- Kubernetes。

这些限制来自当前业务规模，不表示未来永远禁止使用。

## 14. 架构确认结论

**已确认**：v1 采用以下架构组合：

1. **系统形态**：Vue 3 SPA 加 Spring Boot 模块化单体，按业务模块组织并在模块内适度分层。
2. **数据存储**：MySQL 保存全部业务事实；Redis 保存 JWT Token 会话、Refresh Token 状态和撤销信息；附件保存在受后端保护的本地持久化目录。
3. **一致性机制**：状态变化使用 MySQL 事务和乐观并发控制，超时由 Spring 定时任务幂等处理，不引入分布式锁、消息队列或任务平台。
4. **认证方式**：Spring Security + 短期 JWT Access Token + 可轮换 Refresh Token；Redis 支持会话校验和立即撤销。
5. **运行边界**：v1 单实例、单机可重复部署；测试随业务功能同步建设。

这套组合的主要代价是运行时依赖 MySQL 和 Redis，JWT 撤销与刷新比普通 Session 更复杂，且本地附件限制后端横向扩容；换取的是清晰的一致性边界、可控的账号失效能力，以及能够用于求职展示的完整认证实践。
