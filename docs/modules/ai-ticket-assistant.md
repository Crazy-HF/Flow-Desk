# AI 工单处理辅助：接入分析（2026-10-22）

> 状态（2026-10-23）：单张工单生成、受限历史、日额度、前端预览与草稿入口已写入；真实 MySQL 迁移与 AI 专项测试已通过。全量验收与 10 张样本的人工质量评分仍在进行；真实工单环境保持关闭。

- **已确认**：按“单张工单的 AI 处理辅助”方向推进；先完成方案与虚构工单连通验证，再定业务契约、逐步实现。正式工单业务代码尚未编写。

- **暂时假设**：第一版只处理文字。附件原文、跨工单检索、知识库、自动执行工单动作和会话式多轮对话均不进入首个验证闭环。

- **已确认**：长期目标包括真实工单；首批验证仍只用虚构或脱敏数据。真实工单外发前的告知与数据规则仍待确认，不把长期目标当作当前可直接发送真实内容的授权。
- **已确认**：第一次交付仅在开发、演示环境开启 AI 生成；真实工单环境默认关闭。真实工单启用须在数据规则与验收完成后单独推进，环境开关的配置名待技术设计。
- **已确认**：真实工单上的触发流程必须先向负责人展示拟发送的五项内容，允许删改标题、描述中的敏感信息；负责人再次确认后才向 DeepSeek 发请求。后端在实际发送时重新校验工单权限。

- **已确认**：独立 AI 权限只控制新建议的生成。权限被撤销后，符合“当前/最后负责人 + 工单可见性”条件的用户仍能查看此前保存的建议历史。
- **已确认**：首版每位用户每天最多生成 10 次，限制值可配置，后端在调用 DeepSeek 前检查；日界线、失败请求是否计数以及并发原子计数方式待技术设计。

- **已确认**：首轮开发、演示测试的 DeepSeek API 实际费用预算上限为人民币 5 元；每轮记录调用与平台消耗，接近上限即暂停付费验证。虚构工单探针已发生一次付费调用，实际扣费仍待平台账单确认。
- **已确认**：首版模型输入只含标题、问题描述、分类、优先级和状态。最近处理记录是效果不足时的后续补充候选，当前不送入模型、不实现读取。
- **已确认**：每次成功生成的建议需要保存，并可查看历史；历史只给当前负责人查看，工单进入终态后由最后负责人查看。转交后新负责人可以查看，原负责人不再可以查看；读取时仍须通过工单可见性校验。工单未结束时保留历史，结束后再保留 30 天；保存结构和失败请求是否留元数据仍待设计。
- **已确认**：每条建议历史保存负责人确认后实际发送的五项工单内容快照（含删改后的标题、描述）和对应的 AI 输出；输入快照与输出共用历史查看权限及保留期。提示词模板本身如何版本化待技术设计。

- **已确认**：首版选用 Spring AI 接入 DeepSeek。当前项目为 Spring Boot 3.5.16，已加入 Spring AI 1.0.9；手动探针成功调用 `deepseek-flash` 并取得三部分文本。正式应用的自动装配、结构化解析和失败处理仍待验证。

## 2. 现有代码事实

| 位置 | 已有行为 | 对 AI 接入的约束 |
| --- | --- | --- |
| `ticket.application.service.impl.TicketQueryServiceImpl#detail` | 从认证上下文取得用户，检查 `TICKET_VIEW_OWN` / `TICKET_VIEW_QUEUE` / `TICKET_VIEW_PARTICIPATED`，通过 `TicketMapper.selectVisibleDetail` 同时判断权限与工单关系；无权与不存在都返回 `404/TICKET_NOT_FOUND` | AI 请求必须在服务端重新校验目标工单可见性，不能信任前端已打开详情页，也不能仅凭工单编号读取数据 |
| `TicketQueryServiceImpl#records` | 先复用可见性 SQL，再分页读取该工单时间线 | 若使用时间线，要限定条数和字段；不能直接序列化 `ticket_record` 实体 |
| `TicketDetailResult`、`TicketRecordResult` | 详情含标题、描述、分类、优先级、状态、人员与附件元数据；记录的 `context` 由服务按类型显式选择 | 建立专门的 AI 输入白名单，避免把整个 Result 或附件信息直接发给供应商 |
| `add-processing-record` 与前端动作说明 | 负责人手动提交处理内容后写入工单时间线；提交人和后续接手人都能看到，输入提示包含“这次做了什么、查到什么、下一步打算怎么处理” | AI 建议只能预填可编辑草稿；不得把尚未执行的建议表述为已完成的处理事实，也不能误以为 AI 历史的较窄权限会延续到人工提交的处理记录 |
| `docs/technical-architecture.md` 5.1 | Controller 接收 Command/Query 并返回 Result；业务编排在 `application.service.impl`；外部技术实现在 `infrastructure` | AI 用例需遵守既有模块分层，不把授权或提示词拼装写入 Controller |
| 附件模块 | 文件内容通过后端授权读取；图片、PDF、文本、Office 类型均可能存在 | 首版不读取附件原文；未来若需要，先单独设计类型解析、大小限制与授权边界 |

上述工单模块事实仍适用；当前 `pom.xml` 已加入 Spring AI 依赖，`application.yml` 已有默认关闭的 AI 配置，`src/test/java/com/flowdesk/devtools/DeepSeekManualProbe.java` 是手动探针。`ticket` 模块与前端尚无 AI 业务代码。

## 3. 建议的用户流程与数据流

1. 处理人在一张可见工单的详情页主动点击“生成处理建议”；页面展示拟发送的五项内容，允许删改标题、描述中的敏感信息，处理人再次确认。
2. 后端在实际发送时从当前登录身份重新检查“可使用 AI”与该工单可见性，并校验确认后的输入字段与长度。
3. 后端把确认后的工单内容当作**不可信数据**交给模型；要求模型输出固定结构。
4. 页面显示“生成中”并等待同步响应；后端验证结果结构和长度，把实际发送的五项工单内容快照与成功生成的建议一起保存，再向页面返回结果及“需人工核实”的提示；超时或失败时给可重试错误，不影响普通工单查询或处理。
5. 处理人自行核实、编辑或舍弃；可点“填入处理记录”把选定部分放入现有可编辑表单，再由负责人手动提交。提交后会进入工单时间线并对提交人可见，仍走现有业务动作和权限校验。

**已确认的首版内容**：简短摘要、待核实问题、建议处理步骤。候选字段为 `summary`、`questions`、`suggestedSteps`；字段名、长度和空值规则待 API 契约阶段确定。模型返回的任何内容都不得被解释为权限决定、状态机指令或已核实事实。

### 3.1 首版输入白名单建议

- 首版仅发送：标题、问题描述、当前分类、优先级、状态。
- 后续候选：若首版样本表明信息不足，再评估有限条数的最近处理记录；当前不送入模型，也不实现读取。
- 默认排除：姓名、账号、手机号、邮箱、附件名称与内容、关联工单详情、内部 ID、全部时间线及未经过滤的 `context`。
- 若现有标题、描述或记录正文可能含个人信息，需要在调用前明确外部传输边界；“排除结构化个人信息字段”并不能保证自由文本不含敏感信息。

### 3.2 授权建议

**已确认**：首版只给当前负责人的处理中工单使用，并要求 `TICKET_PROCESS` 与一项新增的独立 AI 权限；前者与 `TicketQueryServiceImpl#toDetail` 的 `canProcess` 条件一致。AI 请求仍须在服务端复核身份、可见性、状态、负责人及权限；待受理队列、历史参与者和员工本人均不在首版生成范围。历史查看只开放给当前负责人，终态由最后负责人查看；转交后原负责人不再可看。独立 AI 权限只控制生成，撤销后仍可依工单可见性和负责人关系看历史。不同拒绝条件的错误口径留待 API 设计阶段明确。不能用前端按钮可见性代替服务端校验。

**代码推论**：AI 历史的权限比工单时间线更窄，必须独立存储与查询，不能写成 `ticket_record` 中的 `PROCESS` 记录。历史查询需要“现有工单可见性 + 当前/最后负责人关系”同时成立，不能只调用 `selectVisibleDetail` 就返回 AI 历史。负责人主动把草稿手动提交为处理记录后，那条新 `PROCESS` 记录才按现有规则对工单提交人可见。

## 4. 实现路径候选

| 路径 | 适合场景 | 取舍 |
| --- | --- | --- |
| 在现有 Spring Boot 后端用 DeepSeek API / 兼容客户端接入，外层封装供应商适配接口 | 首版只接一个模型、同步生成、无需检索 | 依赖少，易看清请求、响应、超时与费用；更换供应商要实现新的适配器 |
| 使用 Spring AI 的 `ChatClient` 与模型适配 | 预计很快接入多个模型、统一观测或后续检索 | 提供统一编程接口，但会增加框架依赖；先核对与当前 Spring Boot 版本的兼容组合 |
| 自建模型或独立 AI 服务 | 有本地部署、数据出境或独立扩缩容要求 | 运维与资源成本明显上升，当前没有证据支持首版采用 |

**已选技术方向**：使用 Spring AI 的 DeepSeek 适配。项目当前 Spring Boot 3.5 与 Spring AI 1.0.x 兼容；Spring AI 2.0.x 面向 Boot 4，当前不直接引入。首批样本使用 `deepseek-flash`；换用 Pro 是后续质量评估的候选，不是当前实现要求。外部模型调用限制在 `infrastructure`，由应用服务负责授权、上下文构建、结果校验与失败映射；不要在工单写事务中等待外部模型。首版同步等待响应，暂不引入流式输出、向量库或消息队列。由于已经决定保存每次生成的建议，后续需要设计独立的 AI 结果存储；模型调用与保存事务的失败边界待确定。

**兼容性检查**：Spring AI 1.0.x 的 DeepSeek 文档示例仍写 `deepseek-chat` / `deepseek-reasoner`，而 DeepSeek 当前文档要求首批使用 `deepseek-flash`；手动探针已证明 Spring AI 1.0.9 能传入该模型名并取得当前响应。Spring AI 1.0 的结构化转换能力与 DeepSeek 当前 API 的 JSON 输出能力不是同一项保证，正式实现仍须做应用侧结构和长度校验，并覆盖空响应、拒绝和截断。

**重试配置**：Spring AI 1.0.x DeepSeek 适配文档列出的默认最大尝试次数为 10；本项目已选择不自动重试，实施时必须显式配置并通过失败用例验证一次点击最多触发一次供应商调用。

## 5. 运行准备与验收门槛

| 准备项 | 首版需要明确或准备的内容 |
| --- | --- |
| 业务样本 | 第一轮固定 10 张虚构或脱敏工单，覆盖信息充分、信息缺失、描述含指令、长文本等情况；每条有人工认可的“应包含 / 不应编造”判断 |
| 数据与供应商 | 供应商所在区域、输入内容的使用与保留政策、项目是否允许将工单正文发到外部；必要时做脱敏或改用符合要求的部署 |
| 凭据与费用 | 用户已确认有 DeepSeek API Key 与余额；服务端密钥只从环境读取，不进入前端、仓库、日志和错误响应；首轮付费验证上限人民币 5 元，记录平台实际消耗并在接近上限时暂停 |
| 稳定性 | 每人每日最多 10 次（可配置，服务端检查）；供应商失败不自动重试，由用户手动重试；输入/输出长度上限、并发限制、超时与失败映射待定；模型失败不能阻断正常工单流程 |
| 历史清理 | 以工单 `ended_at` 为结束时间；`COMPLETED` / `CANCELED` / `CLOSED` 后 30 天清理对应 AI 建议，未结束工单继续保留。定时清理方式与索引待设计 |
| 安全 | 测试工单正文中的提示词注入、跨工单引用、越权读取、敏感信息输出；审计只保留必要元数据，正文日志另行评估 |
| 质量 | Codex 准备固定 10 张样本与评分表并检查结构完整性；用户逐张判断可用性。要求结构完整 10/10、虚构已执行事实 0 条、至少 8/10 经用户判断“稍作修改即可用”；逐张记录摘要准确性、问题相关性、建议可操作性、响应时间和单次成本 |

首个可验收闭环应证明：授权用户可对允许的单张工单生成结构化建议并保存；符合历史查看权限的人可读取该工单的建议历史；未授权用户无法触发模型调用或获知工单存在；模型超时或返回非法结构时工单仍可正常使用；一次生成不会修改工单状态、记录、分类、优先级或负责人。实施时再把这些目标拆成具体测试和真实栈验收步骤。

## 6. 第一实施步分析：先验证 Spring AI 与 DeepSeek 的兼容性

本节保留最初的实施步骤；截至 2026-10-22，依赖、配置与单次虚构工单连通探针已完成，余项见下方实测记录。前面的业务范围、输入输出、权限、保存和演示预算已由用户逐项选定。第一项技术风险是：项目使用 Spring Boot 3.5，而 Spring AI 1.0.x 的 DeepSeek 示例仍采用旧模型名；手动探针已证明其可调用当前选定的 `deepseek-flash` 并取得响应。

建议先做一个不接入工单业务的最小兼容性验证，再落完整功能：

1. 核对 Spring AI 1.0.x 的具体版本、BOM、`spring-ai-starter-model-deepseek` 与项目依赖的兼容情况。密钥只从服务端环境变量读取；生产配置保持 AI 生成关闭。
2. 用一张**虚构**的处理中工单样本，通过 Spring AI DeepSeek 适配发起一次同步调用：显式使用 `deepseek-flash`，关闭自动重试，限制输出长度。记录模型名、响应状态、耗时、token 用量与平台实际消耗，不记录密钥和工单正文到普通日志。
3. 验证返回值能转换为“摘要 / 待核实问题 / 建议步骤”并经过应用侧字段、长度校验；同时核对空响应、截断、拒绝和服务错误的处理方式。若适配器不接受当前模型名或响应格式，先定位兼容问题，不静默切换供应商、模型或接入库。
4. 兼容性验证通过后，再完成独立生成/历史查询 API 契约、AI 历史表与权限迁移、可配置日限额、结束后 30 天清理，以及详情页预览和建议面板。按项目既有分层，在 `ticket.application` 定义用例和模型调用出口，在 `ticket.infrastructure` 放 DeepSeek 适配；业务动作仍由现有工单服务处理。保存结果前重读工单：若调用期间负责人、状态或版本已变化，就按明确的冲突口径处理，避免把过时建议当作当前建议。

### 6.2 2026-10-23 已确认的额度与失败契约

本节取代前文仍写作“待技术设计”的额度和失败口径；完整接口与应用实现仍须按本节落实。

- 日额度按 `Asia/Shanghai` 的自然日计算，每人每日上限默认 10 次、由应用配置。通过前置身份、权限、可见性、状态、负责人、版本和输入校验后，数据库事务原子占额。占额成功后，即使供应商超时、返回错误或输出无效，也计一次；前置拒绝和重复 `requestId` 不重复占额。
- 每次负责人确认生成时创建 UUID `requestId`。`ticket_ai_request` 在用户范围内唯一，同一请求只允许一次供应商调用；同 ID 不同工单、版本或输入摘要必须拒绝。供应商结果不确定、应用中断或保存失败时，不以同一 ID 重发；用户如需再试，应显式重新确认并使用新 ID。
- 模型调用前不持有工单写锁；返回后以短事务锁定工单，重查状态、负责人和版本，符合条件才插入 `ticket_ai_suggestion` 并把请求标为成功。若工单已变化，则请求标为过时、额度已用，不保存可用建议。
- 供应商成功但结果未能保存时，接口报错，页面不得声称已保存。`ticket_ai_request` 只保存请求状态、失败码、输入 SHA-256 等元数据，不保存正文。数据库故障导致请求状态无法可靠写回时，原 `requestId` 视为结果不确定，恢复后不得自动重放供应商调用。
- `V14__add_ticket_ai_assistant.sql` 新增 `TICKET_AI_ASSIST` 权限（默认授予 `IT_SUPPORT`）、`ticket_ai_daily_quota`、`ticket_ai_request`、`ticket_ai_suggestion` 和 `ticket.ended_at` 清理索引。建议历史保存实际发送的五项快照、三部分输出、模型/提示词版本和可用 token 用量；不写 `ticket_record`。终态满 30 天清理建议及其请求元数据，未结束工单保留。
