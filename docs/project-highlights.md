## HL-001 创建工单的幂等防重设计

### 当前状态

**创建幂等已实现，已有步骤③真实栈验收记录；见 PROJECT_STATUS.md 与文末 2026-09-28 状态补充。当前新增后端的全量测试与阶段验收尚未完成。**

### 问题背景

创建工单使用 `POST` 请求。用户重复点击、浏览器超时重试或网络中断后再次提交，都可能让相同内容生成多张工单。只在 Vue 页面禁用提交按钮无法覆盖网络重试、多个页面或绕过前端直接调用接口的情况。

### 设计方案

- Vue 在用户开始一次工单提交时生成 UUID 格式的 `submissionKey`。
- 同一次提交的重试始终复用该键；开始一张真正的新工单时才生成新键。
- 后端将该值保存为 `ticket.submission_key`。
- 数据库使用 `(requester_id, submission_key)` 唯一约束，保证同一用户的同一次提交最多生成一张工单。
- 首次请求成功后，使用相同键重试时返回首次创建的工单结果，不再插入新工单。
- 工单快照、创建记录、附件元数据和后续防重结果必须遵守同一创建事务边界。

### 为什么这样设计

- 防重规则由服务端和数据库最终保证，不依赖前端按钮状态。
- 将提交人纳入唯一约束，不会让不同用户生成的相同 UUID 相互冲突。
- 不为 v1 增加通用幂等表或额外基础设施，复杂度与项目规模匹配。
- 数据库唯一约束可以封住并发请求同时通过应用层查询的竞态窗口。

### 后续实现与测试重点

- 校验 `submissionKey` 的 UUID 格式和必填性。
- 验证串行重复请求返回同一工单。
- 验证并发相同键请求最终只产生一张工单及一条创建记录。
- 验证同一用户使用不同键可以正常创建多张工单。
- 验证不同用户使用相同键互不影响。
- 验证附件保存失败时不会留下不完整工单或孤立文件。

### 简历或面试表达参考

设计工单创建幂等机制：由前端生成提交 UUID，后端结合用户维度建立数据库唯一约束，避免重复点击和网络重试产生重复工单，并通过并发测试验证最终一致的防重结果。

## HL-002 账号启停的幂等与并发安全设计

### 当前状态

**设计已确认，核心状态条件更新已编码；接口契约、管理性前置校验、会话撤销和并发测试尚未完成。**

### 问题背景

管理员可能重复点击启用或停用按钮，客户端也可能因为请求超时而自动重试。若仅采用“先查询、再普通更新”的方式，两个并发请求可能同时通过检查，过期请求也可能覆盖其他管理员刚完成的修改。启用和停用还包含权限校验、停用前业务检查及会话处理，因此不应作为普通用户资料更新处理。

### 设计方案

- 使用独立的业务动作接口：`POST /fd/v1/users/{userId}/actions/enable` 和 `POST /fd/v1/users/{userId}/actions/disable`。
- 在方法上使用 `USER_MANAGE` 权限控制，不将整个用户模块限定为管理员模块。
- 客户端提交其读取到的 `expectedVersion`，服务端以用户 ID、源状态和版本号作为数据库条件执行原子更新。
- 用户已经处于目标状态时直接返回成功，不重复更新 `updated_at` 和 `version`，使串行重复请求满足幂等语义。
- 条件更新成功时切换状态并将版本号加一；更新行数为零时重新查询用户状态。
- 并发的相同动作已经把用户改为目标状态时仍返回成功；若状态未达到目标值，则返回稳定的 `USER_CONFLICT`，避免掩盖真正的并发冲突。
- 用户不存在、参数非法等情况仍返回对应错误，不把所有失败都包装成幂等成功。
- 停用操作后续还需纳入“最后一个可用管理员”保护、未完成工单交接以及会话撤销等业务规则。

### 为什么这样设计

- 启停接口表达的是“让账号达到目标状态”，天然适合按目标状态实现幂等，无需额外引入通用幂等表。
- 数据库条件更新能够封住应用层“先查后改”的并发竞态窗口。
- 更新失败后的状态复查可以区分“相同请求已由并发方完成”和“数据确实发生冲突”。
- 返回 `R<Void>` 可以清楚表达命令执行结果，避免使用 `Boolean` 让调用方猜测 `false` 表示失败、未修改还是已经处于目标状态。
- 独立动作接口便于集中承载停用校验、审计、会话撤销等规则，避免通用更新接口绕过业务约束。

### 后续实现与测试重点

- 完成 `expectedVersion` 的请求契约与参数校验，并进行 Controller 集成测试。
- 验证串行重复启用、重复停用均成功，且第二次请求不修改时间和版本。
- 验证两个相同并发请求对外均成功，但数据库只发生一次有效状态变更和一次版本递增。
- 验证相反方向或其他字段的并发修改不会被覆盖，并返回 `USER_CONFLICT`。
- 验证用户不存在、版本缺失、版本非法和状态异常时的稳定错误响应。
- 完成最后一个可用管理员保护、工单交接和会话撤销，并验证其事务边界及失败处理。

### 简历或面试表达参考

设计账号启停的目标状态幂等机制：以账号状态和乐观版本执行数据库条件更新，并在并发更新失败后复查最终状态，使重复点击、超时重试和相同并发请求能够安全收敛，同时保留对真正数据冲突的识别能力。该表述需在接口与并发测试完成后再作为已实现成果使用。

## HL-003 应用壳：导航声明唯一真源与层级面包屑

### 当前状态

**已实现，并有自动化证据**（单元 33 项、E2E 9 项全绿，含管理员真实点击用例；见 `PROJECT_STATUS.md` 2026-09-21 记录）。

### 问题背景

登录后的界面原本把品牌、身份和业务入口混在一条顶栏里，页面内部又各自拼导航；面包屑只显示"首页 + 当前页"两级，用户在"系统管理"下点完"用户管理"再点"分类管理"时，"用户管理"被直接替换，看不出自己处在侧栏的哪一层。如果让每个组件各自抄一份菜单标题，两边迟早会漂移。

### 设计方案

- 应用壳固定为四段：整幅顶栏（品牌位 + 账户区）、按权限生成的侧栏、面包屑条、主体内容；壳只负责摆位，不读业务数据。
- 导航条目与一级栏目名只在 `frontend/src/constants/authorization.ts` 声明一次；侧栏与面包屑消费同一份声明，面包屑的层级由路由名反查该声明得到，不额外维护菜单副本。
- 面包屑规则：`首页 / 一级栏目 / 页面`；页面下的子路由补一级可点回列表页的父页面；不在导航声明里的路由（403、404）退回 `首页 / 当前页`。
- 一级栏目是"容器"而不是页面，没有目标路由，所以不做成可点击的块，避免出现点了没反应的假入口。

### 为什么这样设计

- 菜单的"唯一真源"放在常量层而不是组件里：权限显隐、面包屑层级、栏目标题三处共用一份数据，改一处不会漏另一处。
- 面包屑表达的是**层级**，不是访问历史；把"每访问一个页面就多一条"的需求挡在外面，避免它退化成没有上限的路径列表（那属于标签栏的职责）。
- 容器级不做成可点击项，是因为它没有目标路由；宁可少一个点击目标，也不给一个空动作。

### 后续实现与测试重点

- 导航条目将来若由后端菜单接口下发（含 `icon` 字段），`NavigationEntry` 已预留字段位，接线时不需要改组件结构。
- 窄屏（≤52rem）外壳版式尚未截图核对，只有 CSS 与单测覆盖，需要补视口级用例。

### 简历或面试表达参考

把后台菜单做成"声明一次、多处消费"：权限侧栏与面包屑共用同一份导航声明并按路由反查层级，从而消除菜单标题与面包屑的两套副本；同时把面包屑限定为层级表达（首页 / 栏目 / 页面），并用单元与端到端用例锁住"同级切换不改变栏目层级"的行为。

## HL-004 角色编码唯一性的并发双重防线

### 当前状态

**设计已确认，角色创建服务正在实现；真实数据库唯一键冲突与并发测试尚未完成。**

### 问题背景

角色编码是 RBAC 中稳定的业务标识，创建时必须唯一。只在应用层先查询编码是否存在，虽然能为普通重复请求返回清晰错误，但两个并发请求可能同时查询到“不存在”，随后一起尝试插入；如果数据库没有唯一约束，最终仍会产生重复角色。

另一方面，如果完全依赖数据库异常，普通重复请求也必须执行一次失败的插入，而且持久层异常可能直接泄漏成 `500`，无法形成稳定的业务接口契约。

### 设计方案

- 应用层创建角色前使用 `selectCount` 检查编码是否已经存在；普通重复请求直接返回 `409/ROLE_CODE_CONFLICT`，提供清晰、稳定的业务反馈。
- 数据库保留 `iam_role.code` 唯一约束，作为并发场景下的最终一致性防线；两个请求即使同时通过预检查，也只能有一个成功插入。
- 将数据库并发竞争产生的 `DuplicateKeyException` 转换成相同的 `409/ROLE_CODE_CONFLICT`，不让可预期的唯一键竞争泄漏成 `500/INTERNAL_ERROR`。
- 不笼统捕获所有 `DataIntegrityViolationException`，避免把非空约束、外键约束等其他数据问题错误包装成“角色编码重复”。当前角色表只有编码这一项唯一键；如果未来增加其他唯一约束，需要进一步根据约束名称精确映射。
- 创建方法运行在 Spring 事务中。插入失败后重新抛出的业务异常属于运行时异常，事务不会提交不完整结果。

### 为什么这样设计

- 应用层预检查负责常规场景下的可读性和用户体验，数据库唯一约束负责封住无法由“先查后写”消除的并发竞态窗口。
- 两层检查不是重复工作：前者不能提供并发正确性，后者也不适合直接作为对外错误响应。
- 精确捕获唯一键异常，能保持错误语义可信，避免掩盖真正的数据库或程序缺陷。
- 统一的业务错误码让前端不必区分“普通重复”和“并发重复”，两种情况都按角色编码冲突处理。

### 后续实现与测试重点

- 服务单元测试：预检查发现重复编码时返回 `409/ROLE_CODE_CONFLICT`，且不执行插入。
- 服务单元测试：插入抛出 `DuplicateKeyException` 时转换为同一业务错误。
- 真实数据库集成测试：验证 `iam_role.code` 唯一约束确实生效，并验证异常不会泄漏成 `500`。
- 并发测试：两个请求同时创建相同编码时，数据库最终只有一条记录，一个请求成功，另一个稳定返回 `409/ROLE_CODE_CONFLICT`。
- 回滚验证：插入或后续步骤抛出运行时异常时，不留下不完整的角色数据。

### 简历或面试表达参考

为 RBAC 角色编码设计应用层预检查与数据库唯一约束的双重防线：预检查提供清晰业务反馈，唯一键封住并发“先查后写”竞态，并将数据库重复键异常精确转换为稳定的 `409` 业务错误；通过真实数据库与并发测试验证最终唯一性和事务回滚。该表述需在相关集成测试完成后再作为已实现成果使用。

## HL-005 RBAC 稳定编码与事务行锁边界

### 当前状态

**设计已确认，角色修改服务正在实现；服务测试与真实数据库并发验证尚未完成。**

### 问题背景

角色编码不仅是展示字段，还会被后端鉴权规则、初始化数据和运维配置作为稳定业务标识使用。如果普通修改接口允许改变编码，已经部署的鉴权表达式可能仍引用旧值，导致数据库展示内容与实际访问控制能力发生偏离。

角色修改还可能与角色删除、用户角色授权或角色权限授权并发发生。仅执行一次普通查询再更新，会在“查询完成、写入尚未发生”的窗口中使用已经过期的角色状态，破坏 RBAC 写操作约定的锁顺序和校验基础。

### 设计方案

- `UpdateRoleCommand` 不声明 `code` 字段，从 HTTP 请求模型入口阻止客户端提交角色编码修改。（2026-09-23 重构前的类名为 `IamRoleUpdateVO`；本次只改类名与包位置，设计不变。）
- 更新 SQL 采用明确的字段白名单，只设置 `name` 和 `description`；即使未来请求模型被误扩展，当前持久化语句也不会顺带修改编码。
- 角色修改在 Spring 事务中先通过 `SELECT ... FOR UPDATE` 读取并锁定目标角色，再执行更新；角色不存在时统一返回 `404/ROLE_NOT_FOUND`。
- `FOR UPDATE` 必须与 `@Transactional` 配套使用，行锁才会持续到整个业务事务提交或回滚，而不是在查询语句结束后立即释放。
- RBAC 写操作统一遵守“角色优先”的加锁顺序，使角色修改、删除及后续授权变更能够基于一致的并发协议进行协调。
- 可空的 `description` 使用显式更新语句写入，保证传入 `null` 时可以真正清空数据库字段，避免实体更新策略忽略空值。

### 为什么这样设计

- 请求模型限制负责缩小外部输入面，SQL 字段白名单负责守住最终写入边界；两层共同保证编码不可修改，避免单点约束在后续重构时被意外绕过。
- 将稳定编码视为业务身份而非普通名称，可以让鉴权代码、数据库授权和审计记录长期保持同一语义。
- 行锁将“确认角色存在”和“修改角色”纳入同一个事务窗口，避免其他遵循相同锁协议的 RBAC 写操作在校验与提交之间改变参与数据。
- 固定锁顺序不仅服务当前角色修改，也为后续用户角色、角色权限授权的并发安全和死锁控制建立统一基础。

### 后续实现与测试重点

- Web 测试：更新请求无法接收或修改 `code`，响应中的编码保持不变。
- 服务测试：修改前调用带 `FOR UPDATE` 的查询，而不是普通 `selectById`。
- 服务测试：目标不存在或 ID 非正数时返回 `404/ROLE_NOT_FOUND`，不执行更新。
- 服务与数据库集成测试：名称和说明可修改，并验证说明能够被显式清空为 `NULL`。
- 真实数据库并发测试：角色修改与删除或授权变更并发时遵守角色优先锁顺序，不基于过期校验结果提交。
- 事务测试：更新阶段抛出运行时异常时，角色修改整体回滚。

### 简历或面试表达参考

将 RBAC 角色编码定义为不可变业务标识，通过“更新请求不暴露编码 + SQL 只允许修改名称和说明”形成双层写入边界；同时在事务内先以 `SELECT ... FOR UPDATE` 锁定角色，并让所有 RBAC 写操作遵守角色优先的固定锁顺序，为授权一致性和并发冲突控制建立统一基础。该表述需在服务与并发测试完成后再作为已实现成果使用。

## HL-006 角色安全删除的分层防线

### 当前状态

**设计已确认，角色删除服务正在实现；外键冲突转换与并发删除测试尚未完成。**

### 问题背景

角色不是孤立数据：它可能被用户角色关系或角色权限关系引用，`SYSTEM_ADMIN` 还承担系统管理基线。若仅按主键直接删除，可能破坏授权关系或移除系统必须保留的管理员角色；若只依赖应用层“先查询引用、再删除”，查询与删除之间仍可能出现新的并发授权。

数据库外键可以阻止非法删除，但若将底层完整性异常直接抛出，接口会把可预期的业务冲突表现成 `500`，既泄漏实现细节，也不利于客户端稳定处理。

### 设计方案

- 删除操作在同一事务中按固定顺序执行：先用 `selectByIdForUpdate()` 锁定角色，再判断是否为 `SYSTEM_ADMIN`，随后检查用户角色与角色权限两类引用，全部通过后才执行删除。
- `SYSTEM_ADMIN` 按稳定的角色编码判断并始终禁止删除，违反保护规则时返回 `409/RBAC_CONFLICT`。
- 角色仍被任一授权关系引用时，不执行删除并返回 `409/RBAC_CONFLICT`。
- 数据库继续保留授权表到角色表的外键约束，作为绕过应用层协议或发生并发竞态时的最终防线。
- 删除语句抛出的 `DataIntegrityViolationException` 被转换为 `409/RBAC_CONFLICT`，避免可预期的引用冲突泄漏为 `500/INTERNAL_ERROR`。
- 异常捕获范围只包围父角色删除语句。按当前数据库结构，该语句的完整性失败对应授权关系引用；若未来角色表增加其他删除约束，需要按具体约束名称进一步细分错误映射。

### 为什么这样设计

- 先锁角色再检查保护与引用，使校验建立在事务内的稳定角色状态上，也符合 RBAC 写操作“角色优先”的统一加锁协议。
- 应用层检查负责给出清晰业务语义，数据库外键负责阻止任何路径产生悬空授权，两者分别解决可理解性和最终完整性问题。
- 保护角色检查早于引用检查：即使 `SYSTEM_ADMIN` 暂时没有引用，它仍然因系统规则不可删除，而不是因为当前数据状态碰巧不可删除。
- 创建与删除采用不同的异常边界：创建只捕获更精确的 `DuplicateKeyException` 来表达编码重复；删除父记录时，仅在删除语句周围将完整性异常解释为引用冲突。

### 后续实现与测试重点

- 服务测试：删除前必须调用 `selectByIdForUpdate()`，目标不存在时返回 `404/ROLE_NOT_FOUND`。
- 服务测试：`SYSTEM_ADMIN` 无论是否存在引用都返回 `409/RBAC_CONFLICT`，且不执行删除。
- 服务测试：存在用户角色引用或角色权限引用时分别返回 `409/RBAC_CONFLICT`。
- 服务测试：删除语句抛出 `DataIntegrityViolationException` 时转换为相同业务冲突，而不是返回 `500`。
- 真实数据库集成测试：验证两类外键均能阻止被引用角色删除，并验证无引用的普通角色可以删除。
- 并发测试：授权写入与角色删除竞争时，最终不能出现悬空授权或错误成功响应。

### 简历或面试表达参考

为 RBAC 角色删除建立“事务行锁、系统角色保护、应用层引用检查、数据库外键兜底”四层防线：删除前按固定顺序锁定并校验角色，将外键竞争产生的完整性异常转换为稳定的 `409/RBAC_CONFLICT`，避免悬空授权和底层异常泄漏。该表述需在真实数据库与并发测试完成后再作为已实现成果使用。

## HL-001 补充：响应丢失重试与并发提交（2026-09-28）

### 当前状态

**创建基础与幂等逻辑已实现，已有步骤②③真实栈验收记录。** 下文描述记录了实施时的方案推导，计划措辞按文末状态补充理解；当前分支整体尚未通过全量测试或阶段验收。

### 响应丢失为什么需要复用提交键

员工提交工单后，后端可能已经提交数据库事务，但成功响应在网络传输中丢失。此时前端看到超时，无法判断工单是否创建成功；重试必须继续使用原来的 `submissionKey`，不能重新生成 UUID。

```text
第一次请求：员工 A + 提交键 K → 创建工单 001 → 事务提交 → 响应丢失
重试请求：  员工 A + 提交键 K → 查询原工单 → 返回工单 001 的首次创建结果
真正新提交：员工 A + 提交键 L → 创建另一张工单
```

`submissionKey` 是前端生成的提交标识，数据库约束是：

```sql
UNIQUE (requester_id, submission_key)
```

同一用户、同一个提交键最多保存一张工单；不同用户使用相同键互不影响。提交人从认证上下文获取，查询时必须同时匹配用户 ID 与规范化后的 UUID，不能只按提交键查询。重复请求不覆盖原工单内容，不再次领取每日序号；仍须通过接口输入校验和创建权限校验。

### 并发时为什么查询还不够

两个请求可能同时查到“尚未创建”，所以应用层先查询不能代替数据库唯一约束：

```text
请求 A：查询不存在 → 领取序号 → 插入工单和 CREATE 记录 → 提交成功
请求 B：查询不存在 → 等待每日序号行锁 → 领取序号 → 插入触发提交键唯一约束
                                                        ↓
                                              回滚 B 的整个创建事务
                                                        ↓
                                              新事务查询 A 已提交的工单
                                                        ↓
                                              返回 A 的首次创建结果
```

唯一约束保证最终只有一张工单；创建事务保证工单、首条记录和每日序号一起提交或回滚。并发重复请求分配过的序号随失败事务回滚，不留下多余创建记录。

### 回滚与异常处理边界

- 创建事务内先查询已存在结果；命中时直接返回，只有首次创建才检查分类并执行写入。
- 计划使用 `TransactionTemplate` 明确事务边界：创建事务异常退出并回滚后，在新事务中查询原工单，避免沿用 MySQL 可重复读事务的旧快照。
- 捕获 `DuplicateKeyException` 后，只有按当前用户与提交键找到已创建工单，才可视为幂等成功；找不到则继续抛出异常，不能把编号冲突等其他唯一键异常一律当成重复提交成功。
- 返回首次创建结果：原 `ticketNo`、`PENDING`、版本 `0`、原 `createdAt`。后续工单状态与版本通过查询接口读取，不改变创建重试的返回语义。

### 待验收

同用户同键的顺序和并发请求均返回相同结果，数据库仅一张工单、一条 CREATE 记录；不同用户同键互不串单；原分类停用后合法重试仍返回首次结果；失败的并发重复请求不额外消耗每日序号；无对应提交结果的编号冲突必须报错并回滚。

### 补充：REQUIRES_NEW 与外层事务边界

计划为 `TransactionTemplate` 设置：

```java
transactionTemplate.setPropagationBehavior(
        TransactionDefinition.PROPAGATION_REQUIRES_NEW);
```

`PROPAGATION_REQUIRES_NEW` 表示每次模板执行都开启独立事务；如果调用时已有事务，先挂起已有事务，待本次模板事务结束后恢复。新事务独立提交或回滚，不参与已有事务的提交与回滚。

删除 `create()` 外层的 `@Transactional` 后，普通的、未开启事务的 Controller 调用不会再额外开启那个外层事务；事务由模板执行明确划分：

```text
Controller → create()（无外层事务）
                 ↓
          execute：开启创建事务 T1
                 ↓
          唯一键冲突 → T1 回滚并结束
                 ↓
          catch 在 T1 外处理异常
                 ↓
          execute：开启查询事务 T2
                 ↓
          查询并发方已提交的原工单 → T2 结束
```

普通成功创建只执行 T1；只有唯一键冲突恢复路径才额外执行 T2。若以后由已经开启事务的其他应用服务调用 `create()`，`REQUIRES_NEW` 仍会挂起调用方事务，独立提交的工单不会随调用方后续回滚而撤销，需要按该用例的原子性要求重新评估。

该说明属于尚待落地的幂等方案，不表示 ServiceImpl 已实现或验收通过。

## 查询事务与 @Transactional（2026-09-29）

**最新验收补充（2026-09-29）**：用户已完成详情查询实现；生产编译与真实栈详情 121 项请求/断言通过，0 失败，证据见 `docs/acceptance/2026-09-29-ticket-detail.json`。下方“详情待验收”为写入当时状态；该接口通过不表示事务隔离或驱动优化经过专项实测。

**状态**：工单列表只读事务已实现并通过真实栈接口验收；详情只读事务代码已由用户写入，完整接口验收待执行。以下事务语义是学习与设计说明；未专门验证的隔离/驱动行为不作为实测成果。

### 为什么查询也可能需要事务

分页一般执行两条 SQL：先查总数，再查当前页。如果两条查询之间有并发写入，可能看到不同的数据。MySQL InnoDB 的 REPEATABLE READ 下，同一事务中的普通一致性查询通常复用首次一致性读建立的快照，有助于保持 count 与 items 一致。前提是实际使用该隔离级别与同一事务；READ COMMITTED 下每条一致性查询建立新快照，不能仅凭只读事务保证两条查询一致。

详情目前是一条关联 SQL，不需要额外事务才能保证该语句的一致性；保留只读事务是为了明确查询服务边界与只读意图。以后组合多条查询时，再根据一致性要求决定事务和隔离级别。数据库事务不自动覆盖 Redis 或认证上下文。

### readOnly 的含义

```java
@Transactional(readOnly = true)
```

声明事务只用于读取，供 Spring、事务管理器和驱动处理，某些实现可据此优化。它不是通用的写入禁止机制；是否拒绝写 SQL 取决于驱动、数据库和事务管理器配置。它也不等同于隔离级别、不自动禁止并发修改、不保证查询无需锁等待。

### 常用属性

| 属性 | 含义 | 默认值/行为 |
| --- | --- | --- |
| readOnly | 声明是否只读 | false |
| propagation | 与已有事务如何配合 | REQUIRED：已有则加入，否则新建 |
| isolation | 事务隔离级别 | DEFAULT：由底层数据库决定 |
| timeout | 事务超时，单位秒 | -1：使用底层默认设置，不是统一的 HTTP 请求超时 |
| rollbackFor | 指定触发回滚的异常类型 | 默认回滚 RuntimeException 和 Error，受检异常默认不回滚 |
| noRollbackFor | 指定不触发回滚的异常类型 | 默认无额外排除 |

默认回滚说明适用于当前项目未额外配置全局回滚策略的常规 Spring 事务设置。异常规则可匹配异常及子类；具体规则以最终配置为准。

```java
@Transactional // 普通读写事务
@Transactional(readOnly = true) // 声明只读
@Transactional(rollbackFor = Exception.class) // 包含受检异常的回滚规则
@Transactional(propagation = Propagation.REQUIRES_NEW) // 独立新事务
```

其他传播方式：SUPPORTS 有事务就加入、无事务则非事务执行；MANDATORY 必须已有事务；NOT_SUPPORTED 挂起已有事务后非事务执行；NEVER 禁止在已有事务中执行；NESTED 通常通过保存点提供嵌套回滚，需底层事务管理器支持，无已有事务时按 REQUIRED 处理。REQUIRES_NEW 的独立提交不会随外层事务后续回滚而撤销，不能随意用于需要整体原子性的流程。

隔离级别：READ_UNCOMMITTED 可能脏读；READ_COMMITTED 防止脏读，但同一事务两次查询可能读到不同已提交数据；REPEATABLE_READ 防止不可重复读，幻读与锁行为依赖具体数据库及查询方式；SERIALIZABLE 隔离最强，通常带来更大的并发成本。普通快照查询与 FOR UPDATE 锁定查询不能混为一谈。

### 生效和异常边界

Spring 默认代理模式下，从 Controller 等外部对象调用 Spring Service Bean 的公共方法可触发事务；同一个对象内部直接调用另一个带注解的方法，通常不会触发该方法的新事务配置。private 辅助方法可运行在外部公共方法已经开启的事务里，但自身注解不能依靠默认代理触发事务。

事务内可以使用 try/catch。捕获后重新抛出匹配回滚规则的异常，代理可回滚；吞掉异常并正常返回则可能提交，或因底层已标记 rollback-only 而在结束时失败。当前创建幂等恢复把 catch 放在 TransactionTemplate.execute 外，是为了先结束并回滚失败的创建事务，再开启独立事务回查，不是因为事务中禁止 try/catch。

## IT 工单领取：移除全局角色行锁（2026-09-30）

### 当前状态

**领取路径中的全局角色行锁已从代码移除；本条记录的是代码检查与修复，未据此宣称吞吐量经过专项压测。**

### 如何发现

检查 `TicketServiceImpl.claim()` 的事务调用链时，发现此前 `IamTicketClaimantAdapter.lockEligibleClaimant()` 调用了 `IamRoleMapper.selectByCodeForUpdate("IT_SUPPORT")`。该 Mapper 的 SQL 对 `iam_role` 中编码为 `IT_SUPPORT` 的角色行执行 `SELECT ... FOR UPDATE`。所有 IT 人员都共用这一行，因此即使领取的是不同工单、使用的是不同账号，事务也要竞争同一行锁，后来的请求需等待前一个事务释放锁。这是从代码和 SQL 的锁目标推导出的全局串行风险；先前并发请求的结果受测试账号角色及领取先后影响，不能单独作为该锁造成性能瓶颈的实测证明。

### 如何修复

- `lockEligibleClaimant()` 现在用普通 `selectOne` 按不可修改的角色编码读取 `IT_SUPPORT` 的 ID，不在领取事务里锁住公共角色行。`IamRoleMapper.selectByCodeForUpdate()` 仍可供其他 IAM 写入流程使用，只是领取路径不再调用它。
- 仍用 `selectByIdForUpdate(userId)` 锁定当前用户行，并用 `selectByUserIdForUpdate(userId)` 读取其角色授权，确认账号启用且仍拥有 `IT_SUPPORT`。同一个 IT 账号并发领取不同工单仍可能在自身用户行上等待；不同账号不再因公共角色行而排队。
- 同一工单由 `TicketMapper.claimPending()` 的条件 `UPDATE` 决定胜者：要求工单 ID、预期版本、`PENDING`、负责人为空且领取人不是提交人。成功更新一行后才继续写参与关系和领取记录；未更新到一行按冲突处理。移除公共角色锁不改变同一工单只能被成功领取一次的数据库判定。

### 展示边界

可以表述为“代码检查发现领取事务误锁所有 IT 共用的角色行，改为无锁读取角色 ID，并保留用户授权校验和工单条件更新”。本次仅追加文档，未执行测试或吞吐量对比；不要将它表述为已量化的性能提升。

## HL-007 工单状态动作的「条件更新唯一胜者」（2026-10-06）

### 当前状态

**已实现，并有自动化证据**：单元测试固定判定顺序与冲突响应，集成测试**在真实 MySQL 上用真并发**证明"只有一个人能赢"，真实栈验收另有一条 77/77 的 HTTP 级证据。

### 问题背景

四个动作（`claim` 领取、`add-processing-record` 追加处理记录、`submit-resolution` 提交解决、`confirm-resolution` 员工确认）都会改工单状态或版本。"先查询判断、再更新"在并发下必然出现两个请求都通过判断、后一个覆盖前一个的情况；而显式加锁又会把不同工单的请求也串起来。

### 设计方案

- 判定条件全部下沉到 SQL 的 `WHERE`：`id`、`expectedVersion`、`status`、以及身份条件（`assignee_id = 操作人` 或 `requester_id = 提交人`）。**影响行数只有等于 1 才算成功**，`0` 一律按冲突处理。
- 冲突时用 `SELECT ... FOR UPDATE` 读回当前快照，把 `version`/`status` 放进 `409/TICKET_CONFLICT` 的响应体，前端据此刷新而不是盲目重放——只有快照才能区分"我落后了"和"这条工单已经不是我的了"。
- 状态迁移与不可变时间线在同一事务内完成，记录序号取自条件更新同时递增的 `record_seq`，因此时间线不会出现重复序号。
- 查询侧（`allowedActions`）只做"提示"，动作侧必须重新校验一遍：界面藏按钮不等于接口安全。

### 为什么这样设计

条件更新把"谁赢"交给数据库的唯一判定点，不需要额外锁、也不依赖应用层的时序假设；`version` 同时充当乐观锁与前端刷新信号。相比"锁住整张工单再判断"，它让不同工单的并发互不影响。

### 后续实现与测试重点

真实栈已验证；本阶段补齐的自动化用例覆盖到"同版本并发只有一条记录落库""败者拿到的是库里最新快照""终态四个动作全部 409"。仍未做的是高并发压测（不是 MVP 目标）。

### 简历或面试表达参考

"工单的每个状态动作都用带版本与身份条件的条件更新做唯一胜者判定，影响行数不为 1 即返回 409 并附当前快照；时间线与状态迁移同事务、序号同源递增。并用 Testcontainers 起真实 MySQL 写了 2/6/8 线程的并发用例证明只有一个人能赢。"

## HL-008 确认期限：服务端计算 + CHECK 约束兜底（2026-10-06）

### 当前状态

**已实现，并有自动化证据**（单元测试断言精确期限值，集成测试断言四条 CHECK 约束在动作前后都成立）。

### 问题背景

员工确认期限是业务规则（默认 7×24 小时），但它同时是"状态——期限"这一对字段的完整性约束：待确认必须有期限，非等待态必须没有期限，终态必须没有期限且必须有结束时间。这类跨字段完整性靠应用层自觉很容易被某个新分支破坏。

### 设计方案

- 期限由服务端按 `flowdesk.ticket.confirmation-window` 计算（默认 `7d`，绑定即校验、最小 1 分钟），**不接受客户端传入**；提交解决的时刻是唯一基准。
- 数据库层用 CHECK 约束把状态与期限、结束时间、完成方式绑在一起：`ck_ticket_status_deadline`、`ck_ticket_status_ended`、`ck_ticket_status_completion_method`、`ck_ticket_status_assignee`。写错组合时不是悄悄留下脏数据，而是直接写入失败。
- 动作的 SQL 明确"不触碰不该动的列"：追加处理记录不动期限，提交解决不动 `ended_at`，确认则清空期限并写 `ended_at`。

### 为什么这样设计

把业务规则（多久算超时）留在配置里，把数据完整性（哪些组合非法）放进数据库。前者随环境/验收需要可调，后者不该有任何绕过的路径。

### 后续实现与测试重点

自动超时完成（`AUTO_CONFIRM_TIMEOUT`）与超时关闭属完整版的定时任务，MVP 未实现；期限到期后的行为目前只有“到期不自动改变状态”这一隐含事实。**2026-10-10 用户裁决**：这两个自动任务与**通知 / 通信通道**一并落地（扫描结果要先有通知能力才有意义），在此之前期限只用于展示。工单撤销请求的响应期限是另一条线，同日裁决为**到期即失效**（**待实现**），与本节的自动完成 / 自动关闭不是同一条规则。

### 简历或面试表达参考

"确认期限由服务端按配置计算，客户端无法影响；状态、期限、结束时间、完成方式之间用四条 CHECK 约束固定合法组合，集成测试逐条验证动作前后约束都成立。"

### 当前状态

## HL-011 跨模块不变量：为什么「条件更新」之外还需要固定顺序的行锁（2026-10-07）

### 当前状态

**已实现，并有自动化与真实栈证据（2026-10-07）**：`TicketServiceIT` 覆盖互转并发不死锁、锁后资格复核（并发撤角色）与同版本「转交 vs 撤回」并发；`TicketServiceImplTest` 覆盖锁顺序与双方资格复核；真实栈脚本 `scripts/slice-c-adjust-transfer-acceptance.ps1` 在 8092 上 **127/127 断言通过、退出码 0**（证据 `docs/acceptance/2026-10-07-slice-c-adjust-transfer.json`）。**但下面的「已知边界」必须与结论一起讲**：固定顺序的行锁挡的是 IAM 侧的 check-then-act，挡不住与工单侧动作之间的交叉死锁。

### 问题背景

转交的写入口是一条带条件的 `UPDATE`（`TicketMapper.transfer`）：

```sql
UPDATE ticket
SET assignee_id = #{newAssigneeId}, version = version + 1,
    record_seq = record_seq + 1, updated_at = #{now}
WHERE id = #{ticketId}
  AND version = #{expectedVersion}
  AND status IN ('PROCESSING', 'WAITING_FOR_REQUESTER')
  AND assignee_id = #{actorId}
  AND requester_id <> #{newAssigneeId}
```

它本身已经是“唯一胜者判定”，于是很容易产生一个疑问：既然最终写入是这条条件更新，为什么 `TicketServiceImpl.transfer` 还要按 `user_id` 升序锁住「当前负责人 + 新负责人」两行，并在锁后复核两人的资格？

### 设计方案

两个层面各自守一批数据、各自封一个竞态，不能互相替代。

| 不变量 | 数据所在 | 由谁保证 |
| --- | --- | --- |
| 版本未被别人推进、状态可转交、操作人仍是当前负责人、新负责人不是提交人 | `ticket` 一张表 | 条件更新：单语句原子，影响行数不为 1 即 `409/TICKET_CONFLICT` |
| 新负责人**启用中**且**仍持有 `IT_SUPPORT`** | `iam_user.status`、`iam_user_role` | 应用层复核（跨表进不了这条 `WHERE`） |
| 操作人自己仍然合格 | 同上 | 锁后复核（`actorLocked`） |

- **跨表资格无法进 `WHERE`**：能否成为负责人取决于 IAM 两张表，`ticket` 的条件更新表达不了；“先查后写”之间的空档必须用行锁堵住，否则就是 check-then-act 竞态。
- **不加锁时的具体交错**：T1 判定 B 合格 → T2（管理端）停用 B 或撤销其 `IT_SUPPORT` 并提交 → T1 的条件更新提交。这次写入在 `transfer` 的 `WHERE` 里全部合法，结果却是工单负责人已经失效，违反 `docs/business-model.md`「停用账号不能领取工单，也不能成为转交目标」与 `docs/kickoff.md` 4.6「只能转交给状态正常、可以处理工单的 IT 支持人员」。
- **`SELECT ... FOR UPDATE` 是当前读**：普通 `SELECT` 在 REPEATABLE READ 下是快照读，连“最新已提交值”都不保证读到；加锁读读到最新已提交版本并持有该行排他锁直到事务提交，才能把“复核”与“IAM 写入”排出确定先后。
- **两侧锁的是同一批行，所以真的互斥**：IAM 的写路径本来就用 `selectByIdForUpdate(userId)` / `selectByUserIdForUpdate(userId)`（账号状态变更、用户角色授权与回收）。于是只剩两种顺序：IAM 先提交 → 复核读到新值返回 `null` → 400/403，转交不发生；本事务先提交 → IAM 的写入阻塞到本事务提交之后，“转交那一刻他确实合格”成立。**“复核通过 → 撤权提交 → 转交提交”这种交叉不可能出现。**
- **锁两行而不是一行**：新负责人那行是上述判定必须锁的；操作人那行是纵深防御——停用/撤权会撤销 Redis 会话，请求通常在认证过滤器就被挡下，剩下的是“已过过滤器、IAM 变更随后提交”的在途窗口（`TicketReadPermissionPort.hasAuthority` 读的是会话快照里的权限码，不是数据库真值）。顺带把 `newAssignee` 摘要（含 `displayName`）作为这次加锁读的结果返回，省掉一次查询。
- **升序取锁 = 防 AB-BA 死锁**：若两个事务各自“先锁自己、再锁对方”，`A 转给 B` 与 `B 转给 A` 并发就是死锁，InnoDB 只会回滚其中一个，用户看到的是本可成功的转交失败。按 `user_id` 升序是与“谁转给谁”无关的全局顺序；`min`/`max` 之后用三元表达式把“按锁顺序拿到的两个结果”重新贴回业务身份——**取锁顺序 ≠ 语义身份**。两行必然不同的前提是“转给自己”“转给提交人”在拿锁之前已被拒（字段级校验先于加锁）。
- **条件更新不能删**：两把 `user` 行的锁挡不住工单侧并发（提交解决结果、员工撤销、超时或异常关闭都不写 IAM 行），“唯一胜者”只能继续由 `transfer` 的 `version/status/assignee_id` 判定。
- **与 IAM 批量授权路径的锁顺序一致**：`IamUserRoleServiceImpl.grantUsers` 先把 `userIds` 去重排序再批量加锁，与本路径同为 user 行升序；本路径读角色用普通 `selectOne`（见 2026-09-30「移除全局角色行锁」条目），不锁公共角色行，因此不形成新的跨模块 AB-BA。

一句话：**行锁守“跨模块资格”这条不变量，条件更新守“工单行”这条不变量；写 IAM 的人不碰 ticket 行，写 ticket 的人也不替 IAM 做判定。**

### 为什么这样设计

- 不变量住在哪张表，防线就放在哪一层：能进 `WHERE` 的（版本、状态、负责人）一律下沉到 SQL，进不去的（跨模块资格）才拿锁——锁的范围被压到最小，不同工单之间的转交互不影响。
- 用“持有同一批行的锁”替代“多读一次最新值”：前者给出的是顺序保证，后者只给出一个可能立刻过期的观察。
- 代价花在低频的转交动作上（两把行锁 + 三次加锁读），而不是高频路径；同一工单的并发仍由条件更新收敛，不靠锁整张表。

### 后续实现与测试重点

- 并发用例（`docs/implementation-plan.md` 9.3 片 C 已登记）：`A 转给 B` 与 `B 转给 A` 真并发时两边都不因死锁被回滚，最终负责人是其中之一，时间线只有一条 `TRANSFER`。
- 资格竞态用例：转交提交与“停用新负责人 / 撤销其 `IT_SUPPORT`”并发时，不允许出现“负责人已失效”的提交结果，两种提交顺序都必须收敛到一致状态。
- 语义耦合待确认：`IamTicketClaimantAdapter.lockEligibleClaimant` 里的 `IT_SUPPORT` 是硬编码角色码。当前 `V2__seed_rbac.sql` 只把 `TICKET_TRANSFER` 授予 `IT_SUPPORT`，与“不能转交给系统管理员”一致；若将来通过动态 RBAC 把该权限授予其他角色，会出现“权限检查放行、资格复核 403”的不一致，届时两处要一起改。
- 退出路径待确认：若工单进行中管理端撤销了当前负责人的 `IT_SUPPORT`，该用户无法再把工单转出，只能依赖管理性交接（`TICKET_ADMIN_HANDOFF` 目前尚未实现）。

### 这条设计的边界（已独立成 HL-012）

固定顺序的行锁挡住了 IAM 侧的 AB-BA，但**挡不住与工单侧动作之间的交叉死锁**——因为持锁顺序会被记录表外键反过来。它于 2026-10-07 由并发用例偶发失败暴露、2026-10-08 在片 D 内修复，**已单独登记为 HL-012**（机制推导、修法、代价与验证都在那一条），引用 HL-011 时按一句话带过即可：**同一模块内所有动作的加锁起点必须统一，只把某一族事务的两把锁按 id 排序是不够的。**

## HL-012 跨路径交叉死锁：从一次偶发并发失败到统一全模块的加锁起点（2026-10-07 发现，2026-10-08 修复）

### 当前状态

**已实现，并有自动化与真实栈证据（2026-10-08，完整状态机片 D）**：`TicketServiceIT` 覆盖「转交 vs 撤回」「转交 vs 关闭」「领取 vs 撤销」三组真并发，并断言**败者一定是 `409/TICKET_CONFLICT`**（用 `singleApiException` 收口：若败者是死锁异常，该断言先失败）；`TicketServiceImplTest` 用跨 mock 的 `InOrder` 把"先工单行、后用户行"的加锁顺序钉死，并覆盖"等锁期间版本已变 → 当场 409、不锁用户行、不写库"；真实栈脚本 `scripts/slice-d-close-cancel-acceptance.ps1` 的两组真并发（员工撤销 vs IT 关闭、IT 转交 vs IT 关闭）实测**赢家唯一、败者 409、无 5xx**（证据 `docs/acceptance/2026-10-08-slice-d-close-cancel.json`，182/182）。

### 问题背景：一次偶发失败，而不是一次猜测

HL-011 的固定顺序行锁上线后，`TicketServiceIT` 里那条"同一张工单上转交与撤回补充请求并发"的用例**偶发失败**。它不是每次都红：两个线程要刚好在对方持锁的窗口里申请对方已持有的行，InnoDB 才会判定成环并回滚一个。失败时的表现不是"数据错了"，而是**调用方拿到 `DataAccessException`（HTTP 表现为 `500/INTERNAL_ERROR`）**，而契约要求的是可立刻重试的 `409/TICKET_CONFLICT`。

这一点值得先讲清楚：**回滚本身是安全的**（事务级原子回滚，版本只 +1、只多一条记录，用例逐条核对了这些不变量）。把它当缺陷处理，理由不是"数据坏了"，而是**失败模式不可重试**——用户看到 500 只会重试或报障，而 409 是界面能自解释、能自动对齐版本重试的信号。分布式/并发问题里，"结果碰巧正确"和"失败模式正确"是两件事。

### 机制：外键把持锁顺序反了过来

| 事务 | 先拿 | 再要 |
| --- | --- | --- |
| T1 转交（修复前） | `iam_user`（原负责人、新负责人两行，按 id 升序 X 锁） | `ticket` 行（条件更新） |
| T2 撤回补充请求（同一个人、同一张工单） | `ticket` 行（条件更新 X 锁） | 同一条 `iam_user` 行（插入 `ticket_record` 时 `actor_user_id` **外键**取共享锁） |

T2 并不"想"锁用户行——它甚至没有读 `iam_user` 的语句。**是外键约束在校验引用时必须对父行加共享锁**，于是写 `ticket_record` 的普通插入隐式变成了"申请 `iam_user` 行的锁"。两条路径的顺序正好相反：`user → ticket` 对 `ticket → user`，首尾相接成环。

定位手段值得一提：从"败者是死锁异常"出发，把 T2 的 SQL 日志和它插入的行一起看，才看到那条插入上没有写、却真实存在的锁请求。**并发问题里最难的不是修，是把"隐式加锁"找出来。**

### 修法：统一所有动作的加锁起点

让转交**先锁工单行**（`TicketMapper.selectClaimConflictSnapshotForUpdate`，拿到锁后先复核 `version`），**再按 `user_id` 升序锁两行用户**：

```
ticket 行写锁  →  [version 复核]  →  iam_user 行锁（升序）  →  条件更新  →  记录 / 参与关系
```

- **为什么这样就够**：其他动作本来都是先拿到工单行（条件 `UPDATE` 自己的写锁，或记录插入时的外键读锁），统一成 `ticket → user` 之后环不存在了。这不是"把锁加得更多"，而是**把顺序变成全模块统一的**。
- **为什么锁后还要复核 `version`**：拿锁是排队，排队期间这张单可能已经被别人推进（领取、提交解决结果、撤销）。`version` 是这一行的变更计数，任何状态迁移都会 +1，因此**锁后版本未变即证明前面读到的状态、负责人、提交人都还是当前值**；变了就当场 409，带着重新读到的快照返回。少了这一步，"先锁工单行"就只是把死锁换成了脏读。
- **代价**：每次转交多一次工单行的加锁读（低频动作，可接受）；锁的持有时间略长，但被锁的只有这一张单的行，不同工单之间不受影响。
- **刻意不做的对称修饰**：`close` 也曾被考虑加 `lockEligibleClaimant` 资格锁（"关单前再确认一次关闭人还是合格 IT"），**否决**——那会先锁 `iam_user` 行，正好把刚拆掉的环重新装回去。关闭方的资格已由条件更新里的 `assignee_id = actorId` 与状态判定保证，不需要再引入一次跨模块加锁。**"两个动作看起来对称，所以给它们加同样的锁"正是这类缺陷的常见来源。**

### 为什么这样设计

- 顺序约定必须是**全模块**的，不是"每一族事务内部自洽"的。HL-011 只保证了 IAM 侧那一族（互转并发）不出环，却没有规定"工单侧动作"的起点，于是两族之间照样成环。
- 工单行是这张聚合的根：所有动作都要改它、或写挂在它下面的记录。**从根开始加锁**是最容易解释、也最容易在 code review 里一眼看出的规则——比"记住每个动作各自锁了什么"可靠。
- 隐式锁（外键、级联）也算加锁。设计加锁顺序时，必须把"这条语句会顺带锁到谁"一起算进去。

### 后续实现与测试重点

- 新增任何"先碰 `iam_user` 再碰 `ticket`"的动作都会复活这个环：`claim` 是当前唯一的例外，它先锁用户行（`lockEligibleClaimant`），但它的工单必须是 `PENDING`，而能与之竞争的动作（提交人撤销）不会去锁用户行，因此不成环——**这条豁免依赖状态机，改变 `claim` 的允许状态时必须重新评估**。
- 断言口径已收紧为"败者一定是 409"：它同时是回归守卫——若将来有人把顺序改回去，死锁回滚会让这条断言先失败，而不是让用户先遇到 500。

### 简历或面试表达参考

“做转交时我按 `user_id` 升序锁住双方用户行来复核跨模块资格，互转并发确实不死锁了。后来一条并发集成用例偶发失败：转交和一个工单侧动作并发时，InnoDB 回滚了其中一个，用户拿到 500。查下来是**记录表的 `actor_user_id` 外键**——另一个动作插入记录时隐式申请了同一条用户行的锁，于是两条路径一个 `user → ticket`、一个 `ticket → user`，正好成环。修法是把加锁起点统一成工单行：所有动作先拿工单行的写锁、复核版本，再按 id 升序锁用户行，环就没了。我同时把这条用例的断言从‘胜者唯一、败者可能是死锁’收紧成**‘败者一定是 409’**——回滚本身数据是对的，但不可重试的 500 是缺陷，这个断言就是防止顺序被改回去的守卫。”"

## HL-013 两阶段撤销：不新增第 8 个状态，用三列请求表达「待批准」（2026-10-08）

### 当前状态

**已实现，并有自动化与真实栈双重证据（2026-10-08，分支 `flow-desk/ticket-two-phase-cancel`；已随 [PR #18](https://github.com/Crazy-HF/Flow-Desk/pull/18) 合并 `main`，合并提交 `2cf1bc1`）**：迁移 `V7` 在空库上通过 `flyway.migrate()` + `validate()`（`DatabaseMigrationIT`，基线 `1,2,4,5,6,7`）；`TicketServiceIT` 在真实 MySQL 上跑通「待补充 → 发起撤销请求 → 批准 → 已取消」（期限与请求三列在同一条 UPDATE 内清空）、「拒绝 / 撤回不动工单」、「关闭 vs 批准撤销」的唯一胜者，以及「`confirmResolution` 时工单上挂着待决申请」；服务层单测覆盖四个新动作的 403/404/409/400 与**409 先于 400**、`allowedActions` 三状态 × 两角色的逐格与 `cancelRequest` 的三字段；前端四格动作与详情「撤销申请待处理」块有单测与两个 E2E 场景。全量 `clean verify` → surefire **1070** + failsafe **158**，`Failures 0 / Errors 0`；前端单测 **200 项**、E2E **24 项全绿**；真实栈 `scripts/slice-e-two-phase-cancel-acceptance.ps1` **178/178、退出码 0**（证据 `docs/acceptance/2026-10-08-slice-e-two-phase-cancel.json`），**未发现产品缺陷**。

**讲解时要说清的一处覆盖缺口**：三组并发里 `close vs approve` 的四次运行全部由「关闭」获胜，"批准赢"那一支只有对称断言、没有实测样本（另两组的两个分支都被实测覆盖过）；集成层那条并发用例不要求特定赢家，所以这个竞争仍然是被覆盖的。

### 业务问题：单方面终止与"唯一出口"的拉扯

片 D 的实现口径是：四种非终态下提交人都可以直接撤销，IT 没有否决权。提出改成两阶段的原因是治理层——IT 已经领取并投入处理，工单却被提交人单方面终止。

但直接取消提交人的权限同样不对：误报、问题自行消失、重复提交这三种情况下，撤销是提交人**唯一**的出口（IT 侧的动作他一个都没有）。所以最终口径按"这张单有没有人负责"分流：

| 状态 | 提交人 | 当前负责人 |
| --- | --- | --- |
| 待受理（无人负责） | 直接撤销 | —— |
| 处理中 / 待确认 | 发起撤销请求，可撤回 | 批准（进入已取消）或拒绝（保持原状态） |
| 待补充 | 发起撤销请求，可撤回 | **不裁决**：批准与拒绝都等员工补充完、工单回到处理中（2026-10-10 裁决，已实现） |
| 三个终态 | 不允许 | 不允许 |

关键判断是：**需要征求同意的不是"撤销"这个动作，而是"终止一个已经有人投入的责任"**。待受理没有投入，因此不需要批准。

### 建模选择：为什么不加第 8 个状态

| 方案 | 代价 |
| --- | --- |
| 新增状态 `CANCEL_REQUESTED` | 7 个状态是业务确认过的口径；新增状态要改所有既有判定（每个 `can*`、`ck_ticket_status_*` 的状态白名单、列表筛选、前端状态标签），并重新回答"它算不算非终态、有没有负责人、期限是什么" |
| `ticket` 上挂三列请求字段 | 必须记得在**所有进入终态的路径**上清空它，否则撞约束 |

选了后者，理由是**"待批准"与"当前状态"是正交的两件事**：处理中的工单可以挂着待决请求，也可以没有，两种都仍然是"处理中"。状态机表达不了这个区分，硬塞进去会让"状态"同时承担两个含义。而挂字段只是多一条"进终态要清"的规则，且这条规则**可以由数据库约束强制**——忘记清就写不进去，而不是悄悄留下一张"已取消但还等着批准"的脏行。

这个选择也和项目既有模式一致：`close_reason` / `completion_method` 同样是"当前态字段留在 `ticket`，事件本身进 `ticket_record`"。

### 三条约束驱动的陷阱（这一轮真正的工作量）

1. **三列同生同灭 + 状态白名单**：`ck_ticket_cancel_request_pair` 禁止"有时间没说明"的半截请求；`ck_ticket_cancel_request_status` 禁止终态上残留待决请求。直接后果：`close`（人工关闭）与 `confirmResolution`（员工确认）**必须**在各自的 UPDATE 里一并清空请求三列——它们原本与撤销毫无关系，不改就会在"关闭一张挂着请求的工单"时报约束错误。
2. **批准必须清 `action_deadline_at`**：来源状态可能是待补充或待确认（这两个状态本身带着期限），而 `ck_ticket_status_deadline` 要求其它状态期限为空。于是批准这一条 UPDATE 同时承担四件事：改状态、清期限、清请求三列、写 `ended_at`——**只能一条写完**，拆开就会短暂落进非法组合。
3. **时间线 context 的 `default` 会抛**：`toRecordContext` 用穷尽 `switch` 把记录行翻译成响应，`default` 抛异常是刻意的守卫。四个新记录类型（发起 / 批准 / 拒绝 / 撤回）必须各自有 `case`，否则不是"少一个字段"，而是**整条时间线 500**。这条守卫在片 A 就抓到过一次同类问题。

### 并发：四个动作抢同一行，但工单不冻结

发起、批准、拒绝、撤回共用同一组条件（版本 + 应当事人 + 允许状态 + `cancel_requested_at IS NULL / IS NOT NULL`），并发时只有一条 UPDATE 能命中，另外两路拿 `409` 并带回当前快照。

一个刻意的取舍：**请求待批准期间 IT 的其它动作照常可用**（记录处理、请求补充、提交解决结果、调整、转交、关闭）。若改成"冻结工单直到批准"，就要引入一种"隐形状态"——所有动作都得先判断它。现在的代价是：IT 推进了工单之后，请求的版本条件失效，提交人必须按新版本重新发起；这比"整张单停摆"更容易解释，也让"批准 vs 关闭"这类竞争仍由既有的唯一胜者机制裁决（集成用例实测：赢家 1 个、败者 409、无 5xx）。

### 权限口径：撤销不是关闭

- 批准 / 拒绝只要 **`TICKET_PROCESS`**，**不要求 `TICKET_CLOSE`**：批准让工单进入"已取消"，不是"已关闭"，与 `close` 的「`TICKET_PROCESS` **与** `TICKET_CLOSE` 同时成立」是两条不同的线。
- 发起 / 撤回用 **`TICKET_REQUESTER_ACTION`**，与补充、确认、未解决同码；身份仍由条件更新里的 `requester_id` / `assignee_id` 决定——**当前负责人即使同时持有提交人权限，也撤不掉别人的请求**。

### 期限：写库，但不自动处置

请求带响应期限（新增配置 `flowdesk.ticket.cancel-request-window`，默认 `3d`、下限 `1m`），由服务端计算并落库展示，**到期不自动改变任何东西**。理由与 4.9 / 4.12 的超时任务同一个：本版本没有定时任务，若在读取时判定"过期即失效"，同一个请求会在不同接口里得到"有效 / 无效"两种结论——多出一条真相来源。超时处置属完整版 backlog 第 3 项，届时与其它两个超时规则一起设计扫描与幂等。**2026-10-10 用户裁决（待实现）**：期限届满后请求即失效——批准、拒绝、撤回三个动作都不再允许，员工可以重新发起并覆盖已过期的那一份（覆盖时补写「已过期」记录）。这条取代原先「过期仍可批准」的口径，落地时现有那条「回填期限已过再批准」的验收探针要**反向断言**。**2026-10-10 集中裁决补完口径（仍未实现）**：「重新发起」不设终身次数上限（同一时刻只允许一个有效请求），过期请求保留在工单上、显示为「已过期」，直到被新请求替换或工单进入终态；IT 列表「待我批准」筛选与本条**同批实施**，并与详情里的批准 / 拒绝**共用同一判定**（本人是当前负责人 + 有未过期待决请求）。另外 v1 **目前没有 IT 侧发现路径**——列表不返回待决请求、也没有「待我批准」筛选，IT 只能在自己的工单详情里看到待批准提示（该筛选的批次见上一句，与到期语义同批）；「到期前提醒」依赖通知通道，属 backlog 第 3 项。同日还有第二条裁决：**待补充期间不裁决**——工单处于待补充时批准与拒绝都不开放，员工补充完、回到处理中再裁决（请求与期限保留），转交与撤回补充请求这两条 4.11 已确认的能力不变。**这条已于同日实现**（`TicketServiceIT.approveCancelWaitsUntilTheRequesterSupplements` 在真实 MySQL 上跑通「待补充批准 409 → 员工补充 → 回到处理中 → 批准 200」；`slice-e` 验收脚本的 a3b 组补了 HTTP 与库两层证据，脚本改动**尚未重跑**）。

### 后续实现与测试重点

- **前端必须一起改**：服务端不再在三种非终态返回 `cancel`，前端动作表若不同步登记四个新动作，员工会**看不到任何动作**（动作区整块隐藏）。这正是"按钮来自服务端 `allowedActions`"这条设计的反面证明：契约改了而界面没跟上时，缺的是入口而不是权限。
- **已实现**：待批准提示与三个决策入口需要的详情 `cancelRequest`（`requestedAt` / `deadlineAt` / `reason`）——请求期间状态不变，界面无法从 `status` 推出"IT 正在等批准"。
- **当时登记、2026-10-10 核对后已补齐**：四个端点的 Web 层用例（`TicketControllerWebTest`）、`canApproveCancel` / `canRejectCancel` / `canWithdrawCancelRequest` 与 `cancelRequest` 的详情断言、"`confirmResolution` 时挂着待决请求"这条组合（`close` 那条已被"关闭 vs 批准"并发用例覆盖，其余分别由 `TicketQueryServiceImplTest` / `TicketQueryServiceIT`（`cancelRequest` 三字段含 UTC 转换）与 `TicketServiceIT.confirmResolutionClearsThePendingCancelRequestAndCompletesTheTicket` 覆盖）。**仍未覆盖的两处交互边界**：① 撤销请求在工单被推进（补充、退回、提交解决结果、调整）后仍然有效；② 转交后由新负责人批准或拒绝——两者只有实现层面的事实、没有用例。
- 新增动作时**不要**把 SQL 参数化成一个 `cancel`：批准与拒绝形状几乎相同，但"批准还是拒绝"就是业务判定本身，参数化会让它从 SQL 里消失（与 `withdrawSupplementRequest` / `supplement` 同一理由）。

### 简历或面试表达参考

“工单原先允许提交人在四种非终态直接撤销，IT 没有否决权。改成两阶段时我面临一个建模选择：加第 8 个状态 `CANCEL_REQUESTED`，还是在工单快照上挂一组请求字段。我选了后者，因为‘待批准’和‘当前状态’是正交的——处理中的单可以挂着请求也可以没有，两者都还是处理中；状态机表达不了这个区分，硬塞会让状态承担两个含义。代价是所有进终态的路径都要清这三列，而我把这条规则交给数据库：`CHECK` 约束要求三列同生同灭、且终态不允许残留请求，忘记清就直接写不进去——结果它真的逼我改了两处看似无关的代码（人工关闭与员工确认），这正是我要的效果。并发的四路（发起 / 批准 / 拒绝 / 撤回）共用一组条件更新，只有一条能命中，其余拿 409；请求期间我刻意不冻结工单，代价是 IT 推进后提交人要按新版本重新发起，换来的是不必引入一个所有动作都得判断的隐形状态。”"
