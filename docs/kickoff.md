# FlowDesk 项目启动分析

> 版本说明（2026-09-18）：项目现分为“求职 MVP”和“完整版”。本文早期使用的“v1/第一版”描述作为完整版业务设计保留；当前实际实施范围以 `docs/implementation-plan.md` 为准。MVP 固定三种内置角色，不实现在线角色/权限管理。

## 1. 项目目的

### 1.1 项目场景

**已确认**：FlowDesk 第一版面向企业内部 IT 支持场景，用于管理员工提交的 IT 服务工单。

### 1.2 业务背景

**已确认**：作为 FlowDesk 的项目业务设定，企业员工日常会遇到账号、软件、网络和办公设备等 IT 问题。如果主要通过口头、电话或即时聊天联系 IT 人员，随着请求增多，处理过程容易分散。该设定用于界定项目要解决的问题，不代表已经针对某家真实企业完成业务调研。

### 1.3 核心问题

**已确认**：FlowDesk 第一版围绕以下常见业务问题展开：

- IT 请求缺少统一入口，可能被遗漏或重复处理。
- 工单由谁负责不够明确。
- 员工无法方便地了解处理进度。
- IT 人员之间交接时缺少完整上下文。
- 问题解决后，处理过程和结果难以查询、复盘。

需要解决的根本问题不是“企业缺少一个工单网站”，而是 IT 服务请求缺少统一、可追踪的处理流程。网站和后端系统是解决这一问题的实现方式。

### 1.4 期望结果

**已确认**：FlowDesk 将分散的 IT 服务请求转化为具有明确状态、负责人和处理记录的工单，使请求从提出到解决形成可追踪的协作闭环。

### 1.5 第一阶段成功标准

**已确认**：

- 能通过一个完整示例演示 IT 请求从提交到结束的全过程。
- 工单在处理过程中始终具有明确状态。
- 需要负责处理时，工单具有明确的当前负责人。
- 相关人员能够看到允许其查看的工单进度。
- 关键业务操作留下可追溯记录。
- 核心流程具有自动化测试，而不仅是页面能够点击。

具体状态名称、角色权限和页面功能将在后续阶段分析，本节不提前确定。

## 2. 使用者及职责

### 2.1 普通员工

**已确认**：普通员工是 IT 问题的提出者。

其核心目标和职责包括：

- 描述自己遇到的 IT 问题。
- 在处理过程中补充必要信息。
- 查看工单处理进度。
- 了解最终处理结果。

员工是否必须确认处理结果才能结束工单，将在业务流程阶段决定。

### 2.2 IT 支持人员

**已确认**：IT 支持人员是工单的主要处理者。

其核心目标和职责包括：

- 找到需要处理的工单。
- 明确由自己负责的工单。
- 与提交人沟通并获取必要信息。
- 排查和处理 IT 问题。
- 记录处理过程与最终结果。

工单采用自主领取、人工分派还是其他分配方式，将在业务流程阶段决定。

### 2.3 系统管理员

**已确认**：系统管理员负责维护系统正常使用所需的人员身份、角色和必要基础配置，原则上不参与普通工单的日常处理。

系统管理员具有系统管理职责，但不默认代替 IT 支持人员承担业务处理职责。

### 2.4 后续扩展原则

**已确认**：普通员工、IT 支持人员和系统管理员是第一版的核心使用者，不是系统未来能够支持的角色上限。

后续可以根据真实业务需要增加 IT 主管或调度员、部门负责人、审计人员、外部供应商等使用者。第一版的业务和技术设计应避免将角色范围永久固定为当前三类，但不提前实现尚未确认的角色、流程和权限。

具体操作权限、角色之间的授权关系以及扩展方式，将在权限和技术设计阶段分别确认。

## 3. 第一版范围

### 3.1 v1 核心成果

**已确认**：普通员工登录后能够提交 IT 问题；工单形成明确的处理责任；IT 支持人员能够记录沟通和处理过程；员工能够查看进度、附件及处理结果；整个过程可追踪，并受到身份与权限约束。

v1 必须交付一条可以实际运行和演示的端到端业务流程，而不是一组互不关联的管理页面。

### 3.2 v1 必须具备的能力

**已确认**：

1. 登录并识别普通员工、IT 支持人员和系统管理员的身份。
2. 普通员工能够描述问题并提交 IT 工单。
3. 相关使用者能够查看和查询其有权访问的工单。
4. 工单能够形成明确的当前处理责任，并允许负责人在业务允许时发生变更。
5. 普通员工能够补充信息，IT 支持人员能够记录排查过程和解决结果。
6. 工单能够从提交走到最终结束，并支持员工确认处理结果。
7. 关键业务操作及责任变化能够追溯。
8. 系统管理员能够维护用户、角色和必要的基础配置。
9. 工单支持简单的单级分类。
10. 工单具有优先级，具体设置和调整规则后续确认。
11. 创建工单或补充信息时可以上传受限制的附件；具有工单查看权限的人才能访问附件。
12. 系统提供按工单状态、优先级、分类和当前负责人统计数量的简单数据概览。
13. 核心业务流程、关键权限和异常情况具有可重复执行的自动化测试。

具体页面、表单字段、状态名称、分派方式、转交权限和结束条件将在后续业务分析中确定。

### 3.3 v1 附件边界

**已确认**：v1 只支持业务所需的常见图片和文档附件，并限制单个文件大小和每张工单的附件数量。

在线预览、图片处理、病毒扫描、断点续传和对象存储集群不属于 v1。允许的文件类型、限制数值、存储方式和文件生命周期将在后续阶段确定。

### 3.4 v1 明确非目标

**已确认**：以下能力不纳入 v1：

- 多企业或多租户。
- 外部客户或外部供应商参与处理。
- IT 资产、设备台账、巡检、备件和现场维修管理。
- SLA、超时催办和自动升级。
- 邮件、短信、企业微信或钉钉等外部通知。
- 知识库和智能推荐。
- 自定义工作流设计器。
- 复杂统计报表、数据导出和可配置大屏。
- 移动端 App。
- 多语言和国际化。
- 工单满意度评分和评价。

这些内容属于暂缓范围，不代表未来禁止扩展。后续只有在核心流程稳定且业务价值明确时，才评估是否加入。

### 3.5 v1 验收标准

**已确认**：

- 三类使用者能够按各自身份使用系统。
- 一张 IT 工单能够从提交走到结束。
- 处理期间可以看到工单状态和责任归属。
- 分类、优先级和受限附件能够参与核心业务流程。
- 沟通内容、处理结果和关键操作能够追溯。
- 无权人员不能查看或操作不属于其权限范围的内容。
- 能够查看限定范围内的简单工单数量概览。
- 核心流程具有可重复执行的自动化测试。
- 项目具有清晰、可重复的本地启动和演示方式。

### 3.6 范围扩展原则

**已确认**：第一版设计应为合理的角色和业务能力扩展保留空间，但不提前实现未进入 v1 的角色、流程、基础设施或通用抽象。

## 4. 业务流程

### 4.1 正常业务路径

**已确认**：v1 的正常业务路径如下：

1. 普通员工描述 IT 问题、选择分类、填写必要信息，并可以上传附件。
2. 员工提交后，系统生成正式工单；此时工单等待 IT 支持人员受理，尚无负责人。
3. 一名 IT 支持人员自主领取工单并成为当前负责人，工单进入处理阶段。
4. 当前负责人排查问题，记录处理过程，并可以要求员工补充必要信息。
5. 当前负责人完成处理后填写解决结果，工单等待提交人确认。
6. 提交人验证问题已经解决并确认结果，工单正式完成。

正常路径可以概括为：

```text
员工提交 → 等待 IT 受理 → IT 人员领取并处理 → IT 人员提交解决结果 → 员工确认 → 工单完成
```

### 4.2 主状态

**已确认**：v1 正常路径包含以下四个主状态（v1 的完整状态集合为**七个**：本节四个，加上「待补充」（4.11）、「已取消」（4.7）、「已关闭」（4.8））：

| 状态 | 业务含义 | 当前负责人 |
| --- | --- | --- |
| 待受理 | 员工已经提交，尚无 IT 人员负责 | 无 |
| 处理中 | IT 人员已领取，正在排查或解决 | 有 |
| 待确认 | IT 人员已提交解决结果，等待员工验证 | 有 |
| 已完成 | 员工主动确认，或超过确认期限后由系统自动完成 | 保留最后负责人 |

异常路径的状态已随后续规则确认：「待补充」「已取消」「已关闭」分别见 4.11、4.7、4.8，v1 状态集合共七个。

### 4.3 受理方式

**已确认**：v1 采用 IT 支持人员自主领取的受理方式，不增加专门负责分派的主管或调度员。

一张待受理工单最多只能被一名 IT 支持人员成功领取。未来可以根据业务需要扩展主管分派、自动分配或指定处理人，但这些方式不属于 v1。

### 4.4 正常路径约束

**已确认**：

- 一张待受理工单最多只能被一名 IT 支持人员成功领取。
- 领取成功后，领取人成为工单当前负责人。
- 只有当前负责人可以提交该工单的解决结果。
- 提交解决结果时必须填写处理结论。
- 只有工单提交人可以确认自己的问题已经解决。
- 已完成工单保留最后负责人和完整处理记录。
- 领取、提交解决结果和确认完成等关键动作必须记录操作人和操作时间。

正常路径之外的员工确认问题未解决、工单转交、员工撤销、IT 异常关闭、待确认超时和终态后续处理规则见以下小节。

### 4.5 员工确认问题未解决

**已确认**：工单处于“待确认”状态时，如果提交人验证后认为问题仍未解决，可以填写原因并将工单退回“处理中”。

退回后的业务规则如下：

- 只有工单提交人可以执行“问题未解决”操作。
- 提交人必须填写未解决原因。
- 工单退回“处理中”后，原负责人保持不变。
- 原负责人继续排查问题，并可以再次提交新的解决结果。
- 之前的解决结果不得被覆盖或删除，必须作为处理历史保留。
- 系统记录操作人、操作时间和未解决原因。
- 同一张工单可以多次经历“提交解决结果、员工确认问题未解决、继续处理”的循环，v1 不限制退回次数。
- 员工确认完成和确认问题未解决是互斥操作；并发发生时只能有一个操作成功，另一个操作应得到工单状态已经变化的提示。

员工确认问题未解决是一次业务事件，不增加独立的“已驳回”状态。状态变化如下：

```text
处理中 → 待确认 → 已完成
           |
           └── 问题未解决 → 处理中
```

如果原负责人无法继续处理，可以使用后续确认的工单转交机制；退回操作本身不改变负责人。

### 4.6 工单转交

**已确认**：v1 采用直接转交。工单当前负责人选择另一名 IT 支持人员并填写原因后，处理责任立即转移，不需要接收方再次确认。

转交的业务规则如下：

- 只有“处理中”或“待补充”工单的当前负责人可以发起转交。
- 只能转交给状态正常、可以处理工单的 IT 支持人员。
- 不能转交给普通员工、系统管理员或当前负责人自己。
- 转交时必须选择新负责人并填写转交原因。
- 转交成功后，新负责人立即承担处理责任。
- 原负责人不能再执行只有当前负责人才可以执行的操作。
- 新负责人能够看到此前完整的沟通和处理记录。
- 系统记录原负责人、新负责人、转交原因、操作人和操作时间。
- 工单可以多次转交，每次转交都必须留下独立记录。
- 转交不改变工单状态，转交前后均保持原有的“处理中”或“待补充”，且不能出现没有负责人的中间状态。
- 转交与提交解决结果等互斥操作并发发生时，只允许一个操作成功；另一个操作应得到状态或负责人已经变化的提示。

状态和负责人变化如下：

```text
处理中（负责人 A） → 直接转交 → 处理中（负责人 B）
待补充（负责人 A） → 直接转交 → 待补充（负责人 B）
```

v1 不允许当前负责人将“处理中”或“待补充”的工单退回无人负责的公共工单池。未来可以根据需要扩展接收方确认、主管分派、跨支持小组转交或其他调度方式，但这些能力不属于 v1。

### 4.7 员工撤销工单

**已确认**：普通员工可以撤销自己尚未结束的工单，但必须填写撤销原因。撤销是业务终止，不是删除，工单及其历史记录必须保留。

**2026-10-08 规则变更（用户确认，取代本节原先「四种非终态都由提交人直接撤销」的口径）**：待受理工单没有负责人，提交人**直接撤销**；一旦已经有人负责（处理中、待补充、待确认），提交人只能**发起撤销请求**，由**当前负责人批准或拒绝**。理由是治理层：IT 已经领取并投入处理的工单不应被提交人单方面终止；但提交人也不能因此失去唯一出口——请求待批准期间工单照常流转，负责人也可以拒绝并写明原因。

允许撤销的状态和结果如下：

| 当前状态 | 提交人可以做什么 | 当前负责人可以做什么 | 结果 |
| --- | --- | --- | --- |
| 待受理 | 直接撤销（填写原因） | ——（没有负责人） | 已取消 |
| 处理中 | 发起撤销请求（填写说明） | 批准，或拒绝并填写原因 | 批准后已取消；拒绝后仍为处理中 |
| 待补充 | 发起撤销请求；也可撤回自己已发起的请求 | **不裁决**：批准与拒绝都等员工补充完、工单回到处理中之后（转交、撤回补充请求照常，见 4.11） | 请求留在工单上，工单仍为待补充 |
| 待确认 | 同上 | 批准，或拒绝并填写原因 | 批准后已取消；拒绝后仍为待确认 |
| 已完成 | 不允许 | 不允许 | 不变 |
| 已取消 | 不允许 | 不允许 | 不变 |
| 已关闭 | 不允许 | 不允许 | 不变 |

撤销的业务规则如下：

- 只有工单提交人可以撤销自己的工单、发起撤销请求、撤回自己的撤销请求；只有当前负责人可以批准或拒绝撤销请求，且**只在这张工单处于“处理中”或“待确认”时**（待补充期间不裁决，见下条）。
- 待受理直接撤销必须填写原因；发起撤销请求必须填写说明；拒绝必须填写原因。撤回自己的请求不需要填写理由。
- 撤销请求**不改变工单状态**：处理中仍是处理中，待补充仍是待补充，待确认仍是待确认，原有期限也保持不变。
- **待补充期间不裁决**（2026-10-10 用户裁决）：工单处于“待补充”时，当前负责人既不能批准也不能拒绝撤销请求——这两个动作只在“处理中”与“待确认”上开放；员工补充完、工单回到“处理中”后裁决权自动恢复，请求本身与响应期限原样保留、不重算。这样安排是为了避免 IT 在等员工补充、手上信息不全的时候终止整张工单。4.11 已确认的两条既有能力不受影响：待补充期间仍可**转交**（决策权随新负责人转移），仍可**撤回补充请求**（回到处理中，裁决随之恢复）。提交人**撤回自己的撤销请求**同样不受限制，三个状态都可撤回。期限届满后批准、拒绝、撤回三条路一起关闭（见下条）。**实现状态：已实现（2026-10-10）**——`TicketMapper.approveCancel` / `rejectCancel` 的状态白名单与 `canApproveCancel` / `canRejectCancel` 都已收窄到「处理中 + 待确认」；证据：`TicketServiceImplTest.approveCancelReportsConflictWhileTicketWaitsForTheRequester` / `rejectCancelReportsConflictWhileTicketWaitsForTheRequester`、`TicketQueryServiceImplTest.detailWithholdsApproveAndRejectWhileTheTicketWaitsForTheRequester`、`TicketQueryServiceIT.pendingCancelRequestSwapsRequesterActionAndOffersDecisionToAssignee`、`TicketServiceIT.approveCancelWaitsUntilTheRequesterSupplements`（真实 MySQL：待补充上批准 409 → 员工补充 → 回到处理中 → 批准 200）。
- 同一张工单同时只能有一个**未过期**的待决撤销请求；在请求的有效期内重复发起应得到状态已经变化的提示，不得静默覆盖已有说明；**请求已过期后重新发起不属于"重复发起"**——它直接替换那一份已过期的请求，不返回冲突（2026-10-10 裁决）。
- 批准后工单进入“已取消”：当前期限清空、写入结束时间、保留最后负责人，处理责任随之终止。
- 拒绝后工单保留原状态与原期限，拒绝原因进入时间线；处理责任不变，IT 继续推进。
- 撤销请求带响应期限（默认 3×24 小时，配置项 `flowdesk.ticket.cancel-request-window`）。**2026-10-10 规则变更（用户裁决，取代原「到期不自动处置、过期仍可批准」的口径）：期限届满后请求即失效**——批准、拒绝、撤回三个动作都不再允许（界面刷新后三个入口消失，请求显示为「已过期」），工单保持原状态、不自动取消；员工可以**重新发起**（新请求直接替换已过期的那一份，不必先人工清理），系统在替换时先补写一条「已过期」的时间线记录（含原发起时间、说明与期限）。「重新发起」**不设终身次数上限**（2026-10-10 裁决）：同一时刻只允许存在一个有效请求，每次到期后都可以再发起一次，旧的那一份被新请求替换。过期的请求在被替换或工单进入终态之前**留在工单上并显示为「已过期」**，不需要人工清理——撤回同样被这条规则关闭（三个动作一起失效），因此不存在「先撤回再重新发起」这条路径。到期前提醒与「没人再动过」的过期请求的自动清理依赖通知与定时能力，属完整版 backlog 第 3 项。**IT 侧发现路径（2026-10-10 裁决）**：IT 列表的「待我批准」筛选与本节到期语义**同批实施**，两者共用**同一个核心判定**——「本人是当前负责人 且 工单上有未过期的待决请求」；权限码（`TICKET_PROCESS`）与上面「待补充期间不裁决」这两条既有条件叠加在它之上，列表筛选与详情里的批准 / 拒绝必须同时成立、同时不成立，不得各写一份判定。**实现状态：待改**——现行代码还没有把期限放进判定，列表也没有这个筛选，待改清单见 `docs/implementation-plan.md` 9.3 的规则变更登记（①～⑧）。
- 提交人撤回请求后，工单回到“没有待决请求”的状态，可以再次发起。
- 请求待批准期间，IT 的其它动作（记录处理过程、请求补充、提交解决结果、调整分类或优先级、转交、关闭）照常可用；**待决请求不因工单被推进而失效**——这些动作只让工单版本 +1，请求三列原样保留，工单停在原状态；其中「请求补充」会让工单进入待补充，此时按上一条暂停裁决，员工补充完、工单回到处理中后负责人拿最新版本即可批准或拒绝。需要「按新版本重新发起」的是**提交人自己的其它动作**（补充、确认、未解决反馈、撤回请求）以及一切并发动作：它们都要求 `version` 与当前值一致，旧版本一律 `409`，这与撤销请求是否失效是两件事。
- 工单进入任一终态时，挂在上面的待决请求一并失效；数据库约束保证终态不可能残留待决请求。**失效不单独产生时间线事件**：人工关闭只写 `CLOSURE`、员工确认完成只写 `COMPLETION`，撤销请求的发起时间、说明与原响应期限已经留在更早的 `CANCELLATION_REQUEST` 记录上（集成用例断言过这条时间线恰好是 `CREATE` → `CANCELLATION_REQUEST` → `COMPLETION`）。
- 转交时撤销请求原样保留，**批准或拒绝的权利随当前负责人转移**：新负责人成为唯一的决策人，原负责人不再持有该动作；请求的响应期限**不因更换负责人重新计算**（与 4.12 对补充请求的写法一致）。
- 当前负责人被停用或失去 IT 支持人员角色后，请求会停在「待批准」且没有人能决策；v1 的出口是 5.2 的管理性交接（为活动工单指定接替人），该能力属完整版 backlog 第 4 项，尚未实现。
- “已取消”是终态，不再允许领取、转交、提交解决结果、确认完成或继续处理。
- 如果撤销前已有负责人，应保留最后负责人和此前处理记录，但不再存在需要继续履行的处理责任。
- 工单内容、附件、沟通记录和操作历史不得因为撤销而删除。
- 系统记录发起人、发起时间、撤销说明、批准或拒绝人、决定时间与拒绝原因；“待受理直接撤销”“发起撤销请求”“批准请求”“拒绝请求”“撤回请求”在时间线上是可以区分的五类事件。
- 撤销、批准、拒绝、撤回，以及领取、转交、提交解决结果、确认完成、关闭等操作并发发生时，只允许一个操作成功；其他操作应得到状态已经变化的提示。
- v1 不支持恢复已取消工单。如果仍需处理，员工应重新提交一张新工单。

状态变化如下：

```text
待受理 ──提交人直接撤销──────────────────→ 已取消
处理中 ─┐
待补充 ─┼─提交人发起撤销请求─→ 当前负责人 ─批准─→ 已取消
待确认 ─┘                                └─拒绝─→ 保持原状态
```

“已完成”表示 IT 已提交解决结果，并因员工主动确认或超过确认期限而完成流程；“已取消”表示请求被终止（提交人直接撤销，或提交人发起、当前负责人批准），不代表问题由 IT 成功解决。

IT 支持人员关闭重复、无效或不属于 IT 范围的工单，属 4.8 的独立异常路径（`close` 动作），不属于本节的撤销。

**实施记录（2026-10-08，两阶段撤销）**：本节的两阶段口径由用户 2026-10-08 确认后实施，中间态建模选择「`ticket` 上的一组可空请求列 + 状态机保持 7 个状态」，没有新增第 8 个状态；权限上提交人侧统一用 `TICKET_REQUESTER_ACTION`，负责人侧统一用 `TICKET_PROCESS`（**不要求** `TICKET_CLOSE`——撤销不是关闭）。契约见 `docs/api-design.md` 6.3/6.4，数据变更见 `docs/database-design.md` 的 `V7` 变更说明，交付与遗留见 `docs/implementation-plan.md` 9.3。**后续轮次已完成收口**：前端动作登记表四格与详情「撤销申请待处理」块、真实栈验收（`scripts/slice-e-two-phase-cancel-acceptance.ps1` 178/178、退出码 0）、契约与状态文档均已落地，并已随 PR #18 合并 `main`（合并提交 `2cf1bc1`）。

**规则补记（2026-10-10）**：本节新增规则正文——(1) 期限语义（原按实现补为「期限不进判定、过期仍可批准」，**同日已被用户裁决取代为「过期即失效」，属待实现**，见本节上方的规则变更与 `docs/implementation-plan.md` 9.3 的待改清单）；(2) 待决请求不因工单被推进而失效；(3) 转交后决策权随当前负责人转移、响应期限不重算；(4) 终态失效不单独写时间线事件——以及一条能力缺口说明（负责人失效后请求悬置，出口是尚未实现的管理性交接）。原 4.7 只写到「不改变工单状态」与「进入终态一并失效」，(2)(3)(4) 三条自实现起就是这个口径：其中 (4) 有集成断言（`TicketServiceIT` 断言时间线恰为 `CREATE` → `CANCELLATION_REQUEST` → `COMPLETION`），而 (2) 与 (3) **目前只有实现层面的事实、没有用例**（片 E 验收脚本不含转交组合），用例待补。同日另有两条规则变更：(5) **待补充期间不裁决撤销请求**——**已于 2026-10-10 实现**（批准 / 拒绝只在“处理中”与“待确认”开放，员工补充完、工单回到处理中再裁决；请求与期限保留，转交与撤回补充请求照常，实现证据写在上面那条规则里）；(1) 的「过期仍可批准」被同日的「过期即失效」取代，**该条仍待实现**。此外，同日还有一次集中裁决把本节口径补完并定了推进顺序：**① 到期语义按「批准 / 拒绝 / 撤回三禁 + 可重新发起且不设终身次数上限 + 过期请求保留显示为『已过期』」落地（待实现）；② 待确认自动完成（4.9）与待补充自动关闭（4.12）与通知 / 通信通道一并落地；③ IT 列表「待我批准」筛选与 ① 同批实施，两者共用同一判定；④ 附件与关联先做关联（轻）、再做附件（重）；⑤ 管理性交接排在 ①③ 收口之后。** 规则正文在本节，排期与批次顺序只写在 `docs/implementation-plan.md` 第 9 节与 `PROJECT_STATUS.md`。

### 4.8 IT 异常关闭工单

**已确认**：未按解决流程完成，而是因 IT 的异常关闭决定或员工逾期未补充信息而终止的工单进入“已关闭”终态。“已关闭”与员工主动撤销形成的“已取消”以及已有解决结果并完成流程形成的“已完成”相互区分。

IT 支持人员手动关闭工单时，v1 支持以下原因：

1. **重复工单**：同一问题已经存在另一张有效工单。
2. **不属于 IT 服务范围**：请求应由其他部门或渠道处理。
3. **无效工单**：测试数据、没有实际问题或明显无法构成有效服务请求的内容。

异常关闭的业务规则如下：

- 只有“处理中”工单的当前负责人可以关闭工单。
- “待受理”工单不能直接关闭，IT 支持人员必须先领取并承担处理责任。
- 关闭时必须选择标准关闭原因，并填写具体说明。
- 选择“重复工单”时，必须关联另一张有效且可查询的工单。
- 工单不能关联自身作为重复工单。
- 被关联的目标工单必须属于同一提交人，避免泄露其他员工的工单信息。
- “暂时无法解决”“处理困难”或“需要其他 IT 人员处理”不能作为关闭原因；这类工单应继续处理或转交。
- 关闭后进入“已关闭”终态，不再允许继续处理、转交、提交解决结果或确认完成。
- 工单内容、附件、处理记录和关闭信息必须保留。
- 系统记录关闭人、关闭时间、关闭原因和具体说明。
- 关闭与撤销请求的批准或拒绝、转交或提交解决结果等操作并发发生时，只允许一个操作成功；其他操作应得到状态已经变化的提示。
- v1 不提供已关闭工单的申诉或恢复。如果员工仍需处理，可以重新提交工单并引用原工单。

状态变化如下：

```text
待受理 → IT 领取 → 处理中 → IT 异常关闭 → 已关闭
```

三个终态的业务含义如下：

| 终态 | 业务含义 |
| --- | --- |
| 已完成 | IT 已提交解决结果，并由员工主动确认或系统超时完成 |
| 已取消 | 员工主动终止请求 |
| 已关闭 | 因 IT 的异常关闭决定或员工逾期未补充信息而终止 |

系统管理员不负责判断 IT 工单是否有效，因此不参与异常关闭。未来增加 IT 主管后，可以再评估主管纠正关闭、恢复工单或处理申诉的权限。

### 4.9 待确认超时

**已确认**：IT 支持人员最近一次提交解决结果后，提交人具有 7×24 小时的确认期限。期限届满时工单仍处于“待确认”，系统自动将其转为“已完成”。

**实现状态（2026-10-10 裁决）：待实现**——本节的自动完成需要定时扫描，而扫描结果要让人知道就必须先有通知能力。用户 2026-10-10 裁决把它与**通知 / 通信通道**一并落地，不单独排期（通道是完整版 backlog 第 3 项的前置，推进顺序见 `docs/implementation-plan.md` 第 9 节）。在此之前期限只用于展示，界面文案必须写明"到期不会自动处理"。

待确认超时的业务规则如下：

- 确认期限从 IT 支持人员最近一次提交解决结果的时间开始计算。
- 员工在期限内确认问题已解决时，工单记录为“员工主动确认”完成。
- 员工确认问题未解决后，工单退回“处理中”，当前确认期限立即失效。
- IT 支持人员再次提交解决结果时，重新计算完整的 7×24 小时确认期限。
- 撤销请求在期限内被批准后，工单进入“已取消”，不再执行自动完成。
- 工单自动完成或自动关闭时，挂在上面的待决撤销请求随之失效（终态不允许残留待决请求）。
- 到期时，只有仍处于“待确认”的工单才能自动完成。
- 系统自动完成时，必须记录完成时间、完成方式和“确认超时自动完成”的原因；操作人记为系统，不能记成员工或 IT 支持人员。
- 自动完成不代表员工明确认可解决结果，数据查询和统计必须能够区分“员工主动确认”和“系统超时完成”。
- 自动完成与员工确认、确认问题未解决、撤销请求的批准或拒绝等操作并发发生时，只允许一个操作成功；其他操作应得到状态已经变化的提示。
- 系统停机导致到期处理没有准时执行时，恢复后仍应补充处理已经到期且仍为“待确认”的工单，具体实现方式在技术设计阶段确定。
- v1 不支持重新打开自动完成的工单。如果问题仍然存在，员工应重新提交工单并引用原工单。

状态变化如下：

```text
待确认 ──员工主动确认──→ 已完成（员工主动确认）
待确认 ──超过 7×24 小时──→ 已完成（系统超时完成）
```

该规则只处理员工对已有解决结果长期不回应的情况，不规定 IT 的受理或解决时限，也不包含超时催办和主管升级，因此不属于 v1 已排除的 SLA 能力。

### 4.10 终态工单与后续处理

**已确认**：v1 不支持重新打开任何终态工单。“已完成”“已取消”和“已关闭”均为不可重开的终态；同一问题再次出现或仍需处理时，员工应创建新工单，并可以关联原工单。

终态及后续处理方式如下：

| 终态 | 后续仍需处理时 |
| --- | --- |
| 已完成 | 新建工单，并可关联原工单 |
| 已取消 | 新建工单，并可关联原工单 |
| 已关闭 | 新建工单，并可关联原工单 |

具体业务规则如下：

- 终态工单的状态、负责人和历史记录不再改变。
- 员工仍然可以查看自己有权访问的终态工单内容、附件和操作历史。
- 员工创建新工单时，可以关联自己有权查看的原工单。
- 员工不能关联自己无权查看的工单，避免泄露其他人的工单信息。
- 新工单具有新的工单编号和独立生命周期，从“待受理”开始。
- 新工单不自动继承原负责人。
- 新工单的分类、优先级、描述和附件根据当前问题重新提供，不自动复制原工单数据。
- 原工单保持不变，但新旧工单之间应能够展示关联关系，方便了解处理上下文。
- 关联原工单不是创建工单的必填条件。

一张工单只表达一次完整的处理生命周期。未来如果真实业务需要，可以再评估限时重开、仅允许特定完成方式重开、原负责人优先处理或主管审批等扩展规则。

### 4.11 请求员工补充信息

**已确认**：当前负责人在处理过程中需要员工提供额外信息时，可以发出明确的补充请求，并将工单从“处理中”转为“待补充”。员工提交有效补充内容后，工单自动回到“处理中”，原负责人保持不变。

状态变化如下：

```text
处理中 ──IT 请求补充──→ 待补充 ──员工提交补充──→ 处理中
```

请求和提交补充信息的业务规则如下：

- 只有“处理中”工单的当前负责人可以请求员工补充信息。
- IT 支持人员必须明确填写需要员工补充的内容。
- 请求发出后，工单进入“待补充”，但继续保留当前负责人。
- 只有工单提交人可以提交所需补充信息。
- 补充内容至少包含文字或一个有效附件，不能提交完全空白的回复。
- 员工提交补充信息后，工单自动回到“处理中”，原负责人继续处理。
- 员工的补充内容、附件、提交人和提交时间必须保留。
- 当前负责人可以撤回不再需要的补充请求；撤回时必须填写原因，工单回到“处理中”。
- “待补充”期间不能直接提交解决结果；如果 IT 支持人员发现不再需要补充，应先撤回补充请求，再继续处理。
- 补充信息、撤销请求的批准或拒绝、撤回撤销请求、工单转交和撤回补充请求等互斥操作并发发生时，只允许一个操作成功；其他操作应得到状态或负责人已经变化的提示。

“待补充”期间允许以下两个既有操作：

- 提交人可以发起撤销请求；经当前负责人批准后，工单进入“已取消”。
- 当前负责人可以直接转交给另一名有效的 IT 支持人员，工单保持“待补充”，已有补充请求继续有效。

员工长期不补充信息时的处理规则见下一小节。

### 4.12 待补充超时

**已确认**：IT 支持人员发出补充请求后，提交人具有 7×24 小时的补充期限。期限届满时工单仍处于“待补充”，系统自动将其转为“已关闭”，关闭原因为“逾期未补充信息”。

**实现状态（2026-10-10 裁决）：待实现**——与 4.9 同一口径：本节自动关闭与**通知 / 通信通道**一并落地，在此之前期限只用于展示，到期不自动改变状态（推进顺序见 `docs/implementation-plan.md` 第 9 节）。通道落地时，本节末"不引入邮件、短信或企业微信等外部提醒"的 v1 边界需一并复核。

待补充超时的业务规则如下：

- 补充期限从 IT 支持人员最近一次发出补充请求的时间开始计算。
- 员工应能看到需要补充的内容和补充截止时间。
- 员工在期限内提交有效补充内容后，工单回到“处理中”，当前补充期限立即失效。
- 撤销请求在期限内被批准后，工单进入“已取消”，不再执行自动关闭。
- 当前负责人撤回补充请求后，工单回到“处理中”，不再执行自动关闭。
- “待补充”期间发生转交时，补充请求和原截止时间保持不变，不因更换负责人重新计算期限。
- 到期时，只有仍处于“待补充”的工单才能自动关闭。
- 自动关闭原因固定为“逾期未补充信息”，操作人记为系统。
- 系统必须记录自动关闭时间、原补充请求和补充截止时间，不能将自动关闭记作 IT 支持人员的手动判断。
- 最后负责人作为历史信息保留，但关闭后不再承担当前处理责任。
- 自动关闭与员工补充、撤销请求的批准或拒绝、工单转交或撤回补充请求等操作并发发生时，只允许一个操作成功；其他操作应得到状态或负责人已经变化的提示。
- 系统停机期间已经到期的工单，应在系统恢复后补充处理。
- v1 不允许负责人直接延长补充期限。如果仍需等待，应撤回原补充请求，回到“处理中”后重新发起补充请求。
- 自动关闭后不支持重开；员工仍需处理时，可以创建新工单并关联原工单。

状态变化如下：

```text
待补充 ──员工提交补充──→ 处理中
待补充 ──超过 7×24 小时──→ 已关闭（逾期未补充信息）
```

关闭方式必须能够区分：

- **IT 手动关闭**：重复工单、不属于 IT 服务范围或无效工单。
- **系统自动关闭**：员工逾期未补充信息。

该规则不引入邮件、短信或企业微信等外部提醒。v1 只在系统页面展示补充要求和截止时间。

## 5. 权限与访问范围

### 5.1 工单查看权限

**已确认**：v1 按照角色职责和实际参与关系控制工单查看范围，具体规则如下：

- 普通员工只能查看自己提交的工单，包括这些工单的内容、附件、处理记录和关联关系。
- IT 支持人员可以查看全部“待受理”工单，以及自己当前负责或曾经处理过的工单。
- 系统管理员负责维护用户、角色、工单分类和基础配置，默认不能查看具体工单内容。
- 系统自动任务仅按照已确认的超时规则处理工单，不属于可登录用户，也不具备人工查看工单的身份。

员工和 IT 支持人员只能访问上述范围内工单的附件及关联工单，不能通过附件地址、工单编号或关联关系绕过查看权限。列表、搜索、统计和详情页面均应遵守同一查看范围。

该规则使工单内容仅对提交人和实际参与处理的 IT 支持人员开放，同时避免系统管理员因配置职责自动获得业务内容访问权。v1 暂不提供 IT 支持人员查看与自己无关的历史工单的权限；后续如出现协作、复盘或审计需要，再单独设计受控的查看能力。

### 5.2 角色操作权限

**已确认**：v1 按照角色职责、工单归属和当前负责人控制业务操作权限，具体规则如下：

- 普通员工只能对自己提交的工单执行员工侧业务操作，包括补充信息、确认解决、反馈未解决、对尚未有人负责的工单直接撤销、发起或撤回撤销请求，以及在新建工单时关联自己有权查看的原工单。
- 所有有效的 IT 支持人员都可以认领“待受理”工单；认领成功后，只有该工单的当前负责人可以记录处理过程、请求或撤回补充信息、提交解决结果、转交工单、手动关闭工单，以及批准或拒绝提交人发起的撤销请求。
- 曾经处理过但已不再是当前负责人的 IT 支持人员只能查看该工单，不能继续执行处理操作。
- 系统管理员只负责维护用户、角色、工单分类和基础配置，不能认领、处理、日常转交或结束工单。停用账号或移除 IT 支持人员角色时，可以在不查看工单内容的前提下为相关工单指定一个或多个接替人并完成管理性交接；该例外只用于避免活动工单保留无效负责人。
- 系统自动任务只能执行已确认的“待确认超时自动完成”和“待补充超时自动关闭”，不能代替员工或 IT 支持人员执行其他业务操作。

所有操作必须同时满足角色权限、工单查看权限、工单当前状态和负责人条件。仅能查看某张工单不代表可以操作；当工单状态或负责人已经发生变化时，原操作权限立即失效。

该规则确保任一时刻只有当前负责人能够推进 IT 处理过程，使责任归属与操作记录保持一致。并发认领、转交或状态变化仍按照前述业务流程中的并发约束处理。
