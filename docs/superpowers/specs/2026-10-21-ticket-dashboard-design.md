# 数据概览设计（2026-10-21）

> 状态：设计已按用户指示写入；接口、页面与测试尚未实现。基线为 `main` 的 `58a59ce`。本文件细化 `docs/api-design.md` 8.5；实际交付前仍以代码和验收结果为准。

## 1. 目的与边界

面向具备 IT 支持身份和数据概览权限的人员，回答“我能看的工单现在有多少、处于什么状态、分布在哪些优先级、分类和负责人名下”。统计对象是**当前工单行**，不是工单记录数、处理次数或趋势。首次交付只提供一个范围内的总数与四类分组，支持创建时间和分类筛选。

接口沿用 `GET /fd/v1/dashboard/tickets`；页面沿用 `/dashboard`。不增加全局管理员报表、跨范围并集、历史时点快照、趋势、SLA、导出、独立统计库、新基础设施或外部通道。工单正文、时间线与附件不进入响应。

## 2. GitHub 工单系统对照与取舍

检索日期：2026-10-21。以下仅借鉴可验证的实现方式；它们各自的权限模型和产品范围不直接搬入 FlowDesk。

| 项目与源代码 | 观察到的做法 | FlowDesk 的取舍 |
| --- | --- | --- |
| [Frappe Helpdesk `dashboard.py`](https://github.com/frappe/helpdesk/blob/develop/helpdesk/api/dashboard.py) 与 [页面 `Dashboard.vue`](https://github.com/frappe/helpdesk/blob/develop/desk/src/pages/dashboard/Dashboard.vue) | 服务端限制非经理查看其他代理或团队的统计；数字卡、分类图和趋势分别取数；页面区分整体空态与单图空态。 | 借鉴服务端授权、统一筛选条件和明确空态；当前只做单范围数量，不引入经理组织视角或趋势。 |
| [Znuny `TicketGeneric.pm`](https://github.com/znuny/Znuny/blob/dev/Kernel/Output/HTML/Dashboard/TicketGeneric.pm) | 面板计数复用工单搜索条件，以 `COUNT` 返回摘要；代码还提供带 TTL 的面板缓存。 | 借鉴“先确定搜索范围再计数”；先直接查 MySQL，不因尚无性能证据加入缓存。 |
| [GLPI 工单统计文档](https://github.com/glpi-project/doc/blob/master/source/modules/assistance/statistics.rst) | 将总体数量与按工单属性的分组统计区分展示，支持按负责人等维度查看。 | 保留“总数 + 分组”的清晰结构；暂不引入处理时长、满意度和跨组织分析。 |

**核心判断**：FlowDesk 已有四种工单列表范围，其中概览只采用三个 IT 范围。直接复用列表可见性语义，比照搬竞品的团队/组织筛选更符合现有 RBAC 和最小权限边界。

### 方案取舍

| 方案 | 收益 | 代价与结论 |
| --- | --- | --- |
| **A：一次选一个既有 IT 范围（采用）** | 与列表权限、总数和筛选可逐项对账；不产生跨范围重复计数 | 用户需切换范围查看不同工作视角；符合本版目标 |
| B：三个范围合并为“全部可见” | 首屏可给一个合计数 | 我负责与我参与有重叠；须新增去重、组合授权和新列表语义，本版不采用 |
| C：新增组织级全局报表 | 管理层可横向查看所有负责人 | 超出 8.5 的管理员数据边界，还需额外组织维度和授权模型，本版不采用 |

## 3. 范围、权限与筛选

`scope` 是必填枚举，单次请求只能选择 `PENDING_QUEUE`、`ASSIGNED_TO_ME`、`PARTICIPATED_BY_ME` 之一；不接受 `REQUESTED_BY_ME`，也不把三个范围合成一个默认“全部”。原因是“我负责的”与“我参与的”有重叠，并集需要另一套去重和权限组合规则，且无法直接与列表对账。

认证与权限按以下顺序判断：未登录为 `401`；无 `DASHBOARD_VIEW`、无 `IT_SUPPORT` 角色或缺少选中范围的查看权限为 `403`；范围缺失、无效或使用 `REQUESTED_BY_ME` 为 `400/VALIDATION_FAILED`。`PENDING_QUEUE` 还要求 `TICKET_VIEW_QUEUE`；其余两个范围要求 `TICKET_VIEW_PARTICIPATED`。`SYSTEM_ADMIN` 本身不获得概览权限；多角色管理员仍须满足上述全部条件。若将来要允许“有自定义权限但没有 IT 角色”的用户查看，须单独修改 8.5 的已确认边界。

范围谓词与现有 `TicketMapper.selectScopedPage` 一致：待受理只取 `status=PENDING`；我负责的只取 `assignee_id=当前用户`，包括仍保留最后负责人的终态工单；我参与的用 `ticket_participant` 中当前用户的存在性判断，避免一次转交产生重复计数。当前用户 ID 从认证上下文读取，不接受 `userId`、`assigneeId`、`teamId` 等指定他人的参数。`IT_SUPPORT` 身份须由 IAM 侧可信数据核验；现有 `AuthPrincipal` 只含用户标识/会话信息，不能把前端角色标签当作服务端证据。实现时遵守既有跨模块端口方向。

可选参数只有 `createdFrom`、`createdTo`、`categoryId`。时间使用带偏移量的 ISO 8601 值转 UTC，与工单列表相同；双端均为包含边界，`from > to` 返回 `400`。`categoryId` 为正整数；合法但无匹配工单返回空统计，不将“停用分类”视为无效。未传时间条件表示不限制创建时间，不暗设“近 30 天”。不接受客户端自选状态、优先级、负责人或排序参数作为本接口筛选。

## 4. 统计定义与响应契约

先在服务端确定选中范围和可选筛选下的工单集合 `S`。`total = |S|`；状态、优先级、当前分类、当前负责人四组分别对同一个 `S` 分组，且每组计数总和均等于 `total`。终态工单使用**当前**状态、优先级、分类和保留的最后负责人；不从时间线重算历史分类或历史负责人。分类被停用、负责人账号被停用或改名，不改变该工单是否计入；展示名取当前关联行。

响应仍包在项目现有 `R<T>` 中，`data` 形状建议固定为：

```json
{
  "scope": "PARTICIPATED_BY_ME",
  "total": 3,
  "byStatus": [{ "status": "PROCESSING", "count": 2 }, { "status": "COMPLETED", "count": 1 }],
  "byPriority": [{ "priority": "HIGH", "count": 1 }, { "priority": "MEDIUM", "count": 2 }],
  "byCategory": [{ "category": { "id": 7, "name": "办公设备" }, "count": 3 }],
  "byAssignee": [
    { "assignee": { "id": 12, "displayName": "李工" }, "count": 2 },
    { "count": 1 }
  ]
}
```

最后一条 `byAssignee` 没有 `assignee` 字段，表示“未分配”；契合项目 `non_null` JSON 约定。`PENDING_QUEUE` 的负责人组自然只有“未分配”；`ASSIGNED_TO_ME` 通常只有当前用户，不能因此省略该字段组。没有数据时 `total=0`、四个数组均为空；只返回命中的分组，不补零值行。计数为非负整数，后端使用足以容纳数据库 `COUNT` 的整型。

状态按工单状态机顺序输出：`PENDING`、`PROCESSING`、`WAITING_FOR_REQUESTER`、`WAITING_FOR_CONFIRMATION`、`COMPLETED`、`CANCELED`、`CLOSED`；优先级为 `HIGH`、`MEDIUM`、`LOW`。分类和负责人按数量降序、再按 ID 升序；负责人空值在同数量时排在有 ID 之后。编码和 ID 是稳定分组键，名称只用于显示。

## 5. 后端与数据方案

在 `ticket` 查询侧新增独立的概览查询/结果、服务接口和 Mapper 聚合，不把整个分页列表取到 Java 再计数。应用服务负责参数校验、当前用户和角色/权限核验、时间转换、排序与响应组装；Mapper 对选中范围使用与列表同一套可见性谓词。共享可见性条件时保持 SQL 范围分支一致，后续列表范围变更须同步检查概览。聚合读取可用同一只读一致性快照，避免并发修改时总数与四组短时不符；测试时用固定数据逐组对账。

现有索引已经覆盖队列、当前负责人、历史参与者及分类/状态的主要访问路径（`docs/database-design.md` 第 23 节）。先在代表性数据上检查 `EXPLAIN`、扫描行数和耗时，再决定是否需要新增迁移；设计阶段不预设新索引。当前规模不引入缓存、预计算表或后台刷新任务。若后续使用缓存，缓存键必须同时包含用户、范围、筛选和权限变更语义，不能共享全局统计结果。

## 6. 前端页面与交互

`/dashboard` 从占位页替换为工单领域页面，沿用 `AppPage`、现有 HTTP 封装、权限状态、设计 token 与导航。页面先显示标题和紧凑筛选区：**范围**、创建时间、分类、查询/重置；其下是醒目的总数，再按状态、优先级、分类、负责人四组展示数量。各组以可读的数字和文字为主体，图形只辅助比较，不用趋势线、百分比或虚构的“实时”标识。桌面充分利用工作区，窄屏纵向排列，不回到旧的 70rem 居中大卡片布局。

范围选项只显示当前账号具备相应列表权限的三种范围，优先选 `PENDING_QUEUE`，若不可用则选第一个可用范围；同时要求 `DASHBOARD_VIEW` 与 IT 身份才展示导航和页面。服务端仍独立鉴权。切换范围或时间时清除分类筛选，避免旧分类条件让新范围看似无数据。

现有 `/categories/options` 只返回启用分类，不能作为本页完整筛选来源。当前范围和时间条件的**未按分类过滤**的 `byCategory` 结果形成分类选项；选择分类后保留这份选项，仅刷新统计结果。这样停用但仍有历史工单的分类也能选中，不需要新增分类选项端点。没有分类分组时下拉为空。首版不做分组点击钻取：现有工单列表路由只从 URL 读取 `scope`，尚不能保证携带页面全部筛选条件后显示同一集合；避免点击后数字对不上。

空数据时显示 `0` 与明确空态；加载时保留页面结构并显示占位；请求失败提供重试；无范围权限不发请求。页面刷新只拉当前筛选的数据，不轮询。类别/负责人名过长时截断显示并可查看完整名称；窄屏不产生整页横向溢出。正式实施前依 `frontend/AGENTS.md` 和 `.ui-craft/frontend-redesign-handoff.md` 查看本地参考图并做桌面、窄屏截图自查；本次设计已查看五张现有参考图。

## 7. 验收标准

1. 三种范围分别与同条件 `GET /fd/v1/tickets` 的 `totalElements` 对齐；`PARTICIPATED_BY_ME` 中同一用户多次负责同一工单只计一次，范围之间允许重叠但本接口不合并。
2. 同一稳定数据集上，四组各自的数量之和都等于 `total`；筛选与零结果仍满足该恒等式。并发修改期间同一个响应内部保持一致快照。
3. 覆盖待受理无负责人、已取消无负责人、终态保留最后负责人、转交后的参与历史、停用分类、停用负责人、分类改名、创建时间边界与过滤后空结果。
4. 缺少/伪造范围及无效时间为 `400`；无登录为 `401`；缺概览权限、缺 IT 角色、缺范围查看权限为 `403`；管理员角色本身不扩大工单集合。额外指定他人范围的参数不得带来数据扩权。
5. 前端范围切换、查询/重置、停用分类选项、加载/空/失败状态通过组件检查和浏览器验收；1440 与 375 宽度截图核对，无整页横向溢出。后端真实 MySQL 集成测试验证统计 SQL 与隔离；最终按项目门槛执行相关全量回归与真实栈验收。

## 8. 实施边界与分工

实施应从本分支设计经过复核后的最新 `main` 创建独立短期分支，不在本设计分支叠加业务实现。先后端契约与聚合，再前端页面、回归和真实栈验收。涉及 `ServiceImpl` 的业务逻辑遵守根 `AGENTS.md` 的用户主导分工；用户未针对下一实现阶段另行授权 Agent 写入。Git 提交、推送、合并也待单独明确指示。本文件及 8.5 的细化不代表代码已交付。
